# 浏览器测试 —— 只有真浏览器能测的那部分

`tests/run.php` 是纯逻辑，`smoke` / `e2e` 是服务端链路。
这里跑的是它们都够不到的东西：**页面在真实浏览器里的行为**。

有三件事必须用真浏览器才能验，读代码判断不了：

1. **原生容器桥接** —— `window.AppBridge` 在不在、设备 ID 取的是
   `native` 还是浏览器兜底
2. **页内弹层** —— 真的弹出来了吗、点确定/取消回什么、Promise 会不会悬挂
3. **物理返回键** —— 历史哨兵有没有正确放置与回收

> ⚠️ 这套依赖 node + Playwright，**门店服务器上不需要、也跑不了**。
> 部署环境保持零依赖，这里只在开发机上跑。

## 跑法

```bash
# 1. 起本地服务（另开一个终端）
php -S 127.0.0.1:8910 -t wwwroot

# 2. 装 Playwright（一次就够，装在仓库外，不污染部署件）
mkdir -p /tmp/pw && cd /tmp/pw && npm init -y && npm i playwright

# 3. 跑
cd /tmp/pw
node /path/to/repo/tests/browser/container.mjs
node /path/to/repo/tests/browser/flow.mjs
node /path/to/repo/tests/browser/back.mjs
```

环境变量：

| 变量 | 默认 | 说明 |
|---|---|---|
| `BASE_URL` | `http://127.0.0.1:8910` | 被测站点 |
| `CHROME_PATH` | 自动查找 | 指定 Chromium 可执行文件 |

> npm 装的 playwright 版本常常和机器上已有的 chromium 构建号对不上
> （它会去找自己那一版，找不到就让你 `npx playwright install`）。
> `_launch.mjs` 会先去 `PLAYWRIGHT_BROWSERS_PATH` / `/opt/pw-browsers`
> 里找一个能用的，都找不到才交回给 playwright。手动指定用 `CHROME_PATH`。

## 每个脚本各测什么

### `container.mjs` —— 容器契约（25 项）

不打开容器也能测：脚本会**注入一个假的 `window.AppBridge`** 来模拟容器。

- 桥接与 `ui.js` 已加载、加载顺序正确
- 无容器时设备 ID 回落到 `PAD-` 前缀，`source` 为 `browser`
- 注入 `AppBridge` 后重载，`source` 变成 `native` 且取到 ANDROID_ID
- 页内弹层：确定/取消/空值校验/密码型/自定义按钮文案
- 后台 viewport 含 `viewport-fit=cover`
- 两个页面零 JS 报错

### `flow.mjs` —— 后台真实链路（11 项）

需要本地库里有 `admin` 账号且 PIN 为 `admin123`（`php bin/init.php seed`）。

登录 → 操作员 → 重置 PIN → 页内输入框 → 短 PIN 被拦 → 二次确认 → 取消。
**验的是真实调用现场串起来对不对**，不是工具函数本身。

### `piiswitch.mjs` —— 实名开关的提醒（26 项）

会临时改后台配置 `member_collect_pii`，跑完还原为关闭。

验的是「不会被忘掉」这件事：开启前弹窗告知短信未接入、取消则复选框复原、
开启后顶栏出现常驻红条、**刷新页面后红条仍在**（会话恢复走的是另一条路，
只在登录处理里渲染会漏）、关掉开关后红条消失。

### `padcard.mjs` —— Pad 扫卡建会员（29 项）

自己造两张库存卡再跑，跑完清理干净，不留残留。

另外守着两条**查询之间不能串味**的规则：先查一张有效卡再查无效卡时，
上一张的提示必须清掉；扫了卡之后改用手机号查找时，待绑定的卡号必须清空 ——
后者不清会真的记错账（点「启用」把上一张卡绑给这个人）。

四种卡状态各验一遍：伪造卡被拒、扫错二维码提示「卡号不完整」、
库存卡自动展开建卡表单并带出卡号、已激活的卡直接认出会员。
另外验**扫码不支持时的降级** —— 无头 Chromium 没有 `BarcodeDetector`，
正好用来确认这种情况下引导手工输入而不是弹一个空取景框卡住。

### `padexpiry.mjs` —— 有效期与换卡（55 项）

自己造八张卡、三名会员，跑完把卡、会员、流水全删干净。

服务端那几段在 `smoke.php` ⑰ 已经验过，这里验的是**界面把它串起来对不对**：

- 剩 ≤30 天的库存卡，发之前会拦一次；点「换一张」要真的把
  `S.pendingCard` 清掉（残留会把这张快到期的卡绑出去）
- 过期卡的确认框里**直接带出积分与计次** —— 收银员不用再查一遍
- 换卡弹的是**输入框**不是确认框；中途扫错一张，输入框**要留着**
  让他接着扫，不用从头再来
- 换完直接选上这位会员并关闭弹层，且积分一分不少
- 旧卡换过之后就认不出了，不能再换第二次

另外守着两条容易做错的规则：

**① 到期前的提醒必须是「每次都提醒」。** 测试会连扫两次同一张快到期的卡，
断言第二次**仍然**弹提示。做成「提醒过一次就记下不再问」看着更清爽，
但收银员当时跳过的理由（忙、新卡没到、客人不想换）下次根本不成立 ——
一旦记了「已读」，最后一次提醒之后就再没人提，卡直接过期。

**② 超出宽限期必须经理才能换。** 验的是拦得住、话说得清（带上过期日期
与宽限期月数）、被拒之后**旧卡没被动过**、原因空白不放行，
以及成功后记的是 `card_replace_forced` 这个单独的审计动作。

### `tier.mjs` —— 卡片等级、积分倍率与按等级的奖励门槛（36 项）

自己建一个 2 倍的等级、两批卡（带等级 / 不分级），跑完清干净。
钉住三个设计决定：

- **等级属于卡不属于会员** —— 换成不分级的卡，这位会员就不再是金卡
- **倍率叠在全局倍率之上**：同样 € 50，1.5 倍等级拿 75 分而不是 50
- **已经有卡在用的等级删不掉**（删了那些卡就指向不存在的等级，
  而卡面上明明印着）；停用则可以，老卡照常显示

以及：后台能改倍率与送 1 门槛并立刻生效、门槛留空即跟随全局、
**停用再启用不会把门槛悄悄冲掉**（那个按钮只该改一个开关）、
发卡下拉框按等级码精确出现、Pad 扫卡看到等级徽标、
倍率为 1 时不显示倍率、西语界面下等级名跟着变。

> ⚠️ 断言下拉框时按**等级码**匹配，不要按名字数个数 ——
> 跑崩的测试会在库里留下同名等级，按名字数就会撞上残留，
> 报出一个和产品毫无关系的失败。

### `askcard.mjs` —— 查一张卡（28 项）

客人当面问「我这卡还能用吗」。四种卡态各造一张，跑完清干净。守四件事：

- 四种状态各给一句**能照着念**的话，且都说清下一步怎么办
- **只读** —— 反复查过之后，积分/次数/卡态一个字节都没变
- **不显示手机号邮箱** —— 特意给会员填上再查，断言结果里没有
- 西语界面下整条都是西语，**包括服务端生成的进度那句**
  （上线时就是这句中文漏进了西语界面）

> ⚠️ 这个脚本一开始会**把 admin 的语言重置成 NULL**。
> 语言是跟着账号持久化的，上一次跑崩、清理没执行的话，
> 这次一进来就是西语，而断言的是中文 —— 一片红，看起来像功能坏了。
> **凡是断言具体文案的测试，都要自己先把语言摆正。**

### `locate.mjs` —— 找订单（29 项）

**这条主流程之前一条浏览器测试都没有**，其它脚本要么直接
`openMemberModal()` 跳过找单，要么测的是后台。于是把 `index.html` 里的
`<span id="win-label">` 删掉、`pad.js` 里的引用忘了删，谁都没发现，
直到收银员输了个桌号，屏幕上弹出
`Cannot set properties of null (setting 'textContent')` ——
而且异常被 catch 吃掉，「放宽再找」「改用手工录入」两个降级入口
也一起消失，现场看到的是「按钮不见了」。

现在守着：默认停在「桌号」、登录后那些**由 JS 填的文字**已经有内容
（空的话按钮上一个字都没有）、查得到单能走到记账方式、查不到时降级入口
真的出现、放宽再找可用、小票号那条路可用，以及**整条路在西语下再走一遍**。

需要先注入模拟活单（`tests/sim/inject_live.php`）。

### `cachebust.mjs` —— 版本更新怎么落到 Pad 上（16 项）

现场原话：「我点了好久的刷新按钮，但是代码还是老旧的」。
页面改由 PHP 发之后，资源 URL 带 mtime 版本号，这里验的是：

- 每个资源引用都带 `?v=`，文档本身是 `no-store`
- 服务端版本变了 → 停在第一步时**自己刷新**
- **干活干到一半时绝不刷新** —— 已填的金额不能被冲掉
- **同一个版本只刷一次** —— 否则版本号一直对不上时收银机会无限刷新
- 换一个新版本，照常更新（别把上一条守过头变成「以后都不更新」）

### `lang.mjs` —— 多语言（49 项）

跑完把两个测试账号的语言偏好还原成 NULL，不留残留。

- 登录页就能切；`<html lang>` 跟着变
- **切换不能吃掉输入框** —— `data-i18n` 走 `textContent`，
  挂在包着 `<input>` 的 `<label>` 上会把输入框整个抹掉，
  而这个错误在中文界面下完全看不出来
- 服务端的报错也跟着换语言（Pad 带 `X-Lang`）
- **语言记在账号上**：刷新后还在（会话恢复走 `/auth/me`，是另一条路，最容易漏）；
  换台平板登录还是他选的那种；同一台平板换个人则换成那个人的
- 切语言**不冲掉填了一半的东西** —— 重画分配步骤时不能调
  `startAssign()`，它会重置 `S.people`

其中 ④bis 段是**照着店主原话一步步走的**：A 选中文、B 选西文 →
A 登录无视当前语言切中文 → B 登录切西文 → B 改成中文 →
此后两人登录都是中文。每一步同时核对界面显示和 `operator.lang` 的值，
守住「一人一条记录，改自己的不影响别人」。

### `cards.mjs` —— 后台发卡（30 项）

需要 `admin` / `admin123` 能登录后台。

登录 → 生成批次 → 校验印刷清单 → 查卡 → 作废 → 再查确认。
重点验的是**印刷清单的格式**（制表符三列，能直接粘进 Excel）、
**明文 PIN 只显示这一次**的警告确实出现，以及手输把 `0` 打成 `O`
仍能查到同一张卡。

有效期是必填项，所以这个脚本也顺带守着两道校验（不填 / 填成过去的日期）、
生成前的**两道确认**（先核对日期，再警告 PIN 只显示一次），
以及印刷清单变成**四列**这件事。

> ⚠️ 这个脚本会在库里留下一个 `PWxxxx` 批次的 5 张卡（其中 1 张已作废）。
> 跑在开发库上无妨，别对着生产库跑。

### `back.mjs` —— 物理返回键（16 项）

容器的返回键走 `WebView.canGoBack()`。Pad 是单页状态机，不写历史的话
`canGoBack()` 恒为 false —— 收银员在记账任何一步按返回，弹的都是
「确认退出应用」，而不是退回上一步。**这个问题只在容器里出现，
在浏览器上完全看不出来**，所以必须专门测。

- 前进三步后连按返回，逐级退回起点
- 回到起点后哨兵被回收（否则会白按一下返回）
- 弹层优先于步骤：开着弹层时按返回只关弹层，不动步骤
- 返回键关掉 UI 弹层时，其 Promise 正常 resolve 成「取消」，不悬挂

### `carddate.mjs` —— 发卡时的有效期（22 项）

后台印卡那一步。**卡一旦印出去就改不了**，所以这里守的是「按错日期」这件事：

- 日期后面跟一个红色的「距今还有 N 天」——脑子记错年份时，天数会立刻露馅
- 新批次默认落在【两年后的 12 月 31 日】，但只是默认，之前的日期照样能选
- 天数随日期实时变，选到过去的日期要变成警告而不是负数

### `rewardmode.mjs` —— 门槛口径与两个输入框（18 项）

「几次送一次」和「累计消费多少送一次」是两个输入框，但同时只有一个作数。
选了「按次数」，金额那个框必须**变灰不可输入** —— 两个都亮着的时候，
店家会两个都填，然后以为两条规则同时生效。

验的是 `active_when` 这套依赖机制真的接到了界面上：切换口径 → 对侧变灰、
变灰的那个不参与提交、刷新之后灰的还是灰的。

### `merge.mjs` —— 多桌合并计入一人（24 项）

同行分桌：几桌分开结账，最后并给一位客人。**只有经理看得到这个入口。**

- 合并只并【积分】，次数照旧「一张卡一个餐期 1 次」
- 跨餐期 / 超时 / 超过桌数上限都拒，并且说得清是哪一条
- 整组要么全成要么全退 —— 「三桌成了两桌」比失败更难收拾
- 撤销按组撤，不会只撤掉其中一桌

### `visitcount.mjs` —— 计次口径：一张卡一个餐期最多 1 次（16 项）

界面上**根本没有**「整单记一人」这个按钮（它会把同桌其他人的次数
并到一个人名下），以及同一张卡本餐期第二次记账时屏幕要**明说没计次**——
不说的话客人回头问「怎么没给我盖章」，谁也答不上来。

### `session.mjs` —— 熄屏之后还认不认得登录（16 项）

平板熄屏一会儿再打开就要求重新登录。根因在容器侧（WebView 的 Cookie
在 `flush()` 之前只在内存里），但 Web 这边有一条兜底：把令牌另存一份到
`localStorage`，Cookie 丢了就用它。这个脚本守的是那条兜底 ——
读写全都包在 try/catch 里（隐私模式下 `localStorage` 本身就会抛）、
退出登录要把它清干净、令牌不能出现在 URL 或页面文本里。

### `bindamount.mjs` —— 次数与积分绑在一起（22 项）

店主自己推演出来的两个洞，方向相反、代价也相反：

| 形状 | 是什么 | 代价 | 处理 |
|---|---|---|---|
| 有份没钱 | 金额被前面的人分完之后，再提交「€ 0、要 1 份」白拿一次计次 | 店家吃亏 | 🔴 硬拒 |
| 有钱没份 | AA 除不尽时余数堆给第一位 → 后几位付了钱一次都没有 | 客人吃亏 | 🟡 提醒 |

服务端 `portions_without_amount` 才是硬拒那一面的把关
（`AllocationTest` / smoke ㉕）。这里守收银员那一侧：

- 点提交之前就拦住，当场说清是**哪一位**（卡号打码）
- 反面只挂一条**橙色提醒**不拦提交 —— 只点酒水的客人本来就该 0 份，
  用红色会把「必须处理」和「看一眼」混成一档
- 4 份 5 人 → `[1,1,1,1,0]`，**不是** `[4,0,0,0,0]`
- **绕开界面直接调接口，服务端照样拒**

> ⚠️ 每次 `#btn-aa` 重拆都会把 `S.people` 整个重建，**会员选择也跟着没了**。
> 拆完之后要重新选卡，不能沿用上一次的选择。

### `assignlock.mjs` —— 第一界面就把话说清、把数字锁死（43 项）

现场截图：一张只剩 1 份的单，「份数」框里打进了 4。服务端当然会拒，
但那要等到点提交才知道 —— 客人就站在柜台前。

守的是「看得见」与「点不了」两件事：

- 黄框每行带上**份数**与**已计几次**（客人问的是「我这顿算上了吗」，
  而「算上」等于拿到了一份计次套餐；只写金额答不出来）
- 名单里已记掉的那几行画成**灰底虚线、没有「选择会员」按钮**，
  能选的和不能选的一眼分得开，且**分摊之前就看得见**
- AA 默认人数扣掉已记掉的位数；份数框边打边封顶、金额框失焦封顶
- 会员数上限 = 份数；0 份的单只准 1 位，并弹**页内层**告知（不是系统 alert）
- 最后一段绕开界面直接调接口 —— 界面拦得住手滑，拦不住有心人

### `invoicelock.mjs` —— 小票号查单不能当探针用（14 项）

小票号就是 `order_head_id`，连号。原来「超时效」会回一句
「这张小票是 8-16 的」，等于确认这个号是真的，还附送那天有生意。

- 收银员查「超时效的真单」与「不存在的号」，两句话**一字不差**
- 句子里没有日期，也不回显输进去的号
- 经理看到的两句不一样（「有单但超期」/ 带号），且都标着「经理可见」
- **经理那句里也没有日期** —— 只给「在期内 / 在期外」这一个二值；
  经理账号外泄时，泄露面不该比收银员大
- 界面提示里**没有 5 位以上的数字** —— 举一个号当例子，
  等于把「长什么样、数到哪儿了」一起印在屏幕上

> 真正的把关在服务端（按 `is_manager` 砍字段），由 `http_sweep.php` ⑨ 打接口本身；
> 这个文件测的是界面确实照着说了。

## 写这类测试时反复栽过的坑

都是**真的栽过**才写下来的，新加脚本前先看一眼。

### 1. `#toast` 是全局共享的，会读到上一条

它有 3 秒存活期。新动作发生时旧提示往往还挂在那儿，
「等 `#toast` 可见」于是命中的是上一步的结果。

**做法**：先把它清掉再触发动作，然后等**特定文本**。

```js
await clearToast();          // 必须在触发之前
await page.click('#btn-x');
await waitToast(/已作废/);    // 等特定文本，不是「等可见」
```

顺序反了同样会错 —— 在 click 之后再 clear，抹掉的正是刚弹出来的那条。
（`padcard.mjs` 和 `cards.mjs` 先后各栽过一次。）

### 2. `waitForSelector('#x[hidden]')` 永远超时

它默认等的是 **visible**，而 `[hidden]` 的元素永远不可见，于是自相矛盾。

```js
await page.waitForSelector('#member-modal', { state: 'hidden' });   // ✅
await page.waitForSelector('#member-modal[hidden]');                // ❌ 必超时
```

### 3. 元素可能**根本不在 DOM 里**，不是隐藏

后台关闭「允许收集联系方式」时，那一栏是整块**移除**的（有意为之，
让收银员没有索要入口）。`$('#new-phone').value = ''` 于是抛 TypeError，
后面的 `useMember()` 永远执行不到 ——
表现是「提示说建卡成功了，但弹层不关、会员也没选中」。

**这个 bug 只有浏览器测试能抓到**，逻辑测试和 smoke 都看不见。
写产品代码时对可能被移除的元素一律判空。

### 4. 造数据别只改余额

`applyDelta()` 只动余额，不写流水。smoke ⑬ 段有一条不变量
「每名会员的积分余额与其流水合计一致」，只改余额那条断言会红 ——
**而它是对的，造假数据的是测试，不是产品**。

`point_ledger` 里没有 `business_date` 列（写这条 INSERT 时想当然加了，
直接抛异常）。落库前先照着 `db/migrations/001_init.sql` 核一遍列名。

### 5. PHP 从 stdin 喂进去时，致命错误【一个字都不打】

`padexpiry.mjs` 用管道给 PHP 喂造数脚本（省得跟 `php -r` 的引号地狱较劲）。
这么跑的时候，PHP 的 fatal **stdout、stderr 全空**，只留一个 255 退出码 ——
`-d display_errors=stderr` 也救不回来。于是造数一失败就完全没有线索。

解法是自己挂一个 shutdown 钩子，把 `error_get_last()` 打到 stderr：

```js
const probe = 'register_shutdown_function(function () {'
  + ' $e = error_get_last();'
  + ' if ($e !== null && ($e["type"] & (E_ERROR | E_PARSE | E_COMPILE_ERROR)) !== 0) {'
  + '   fwrite(STDERR, $e["message"] . " @ " . $e["file"] . ":" . $e["line"]);'
  + ' }});';
execSync('php', { input: '<?php ' + probe + code, ... });
```

真栽过：造数里一句 `generateBatch` 撞了重复批次号，
界面上只有「Command failed: php」六个字，查了半天。

### 6. 模板字面量里的 PHP 命名空间要写双反斜杠

造数脚本嵌在 JS 的模板字面量里，`\C` 这种未知转义会被 JS **吃掉反斜杠**：

```js
php(`... Vip\CardNumber::normalize($x)  ...`)    // ❌ 变成 VipCardNumber
php(`... Vip\\CardNumber::normalize($x) ...`)   // ✅
```

报错是 `Class "VipCardNumber" not found`，看着莫名其妙 —— 记住这一条就够了。

### 7. `waitForNavigation()` 在这个项目里会误判

Pad 的物理返回键靠往历史里放哨兵实现（`ui.js` 的 `pushState` / `history.back`），
**每次切步骤都会触发一次 `framenavigated`** —— URL 压根没变，
但 `page.waitForNavigation()` 照样 resolve。
拿它判断「页面有没有真的重新加载」，结论会完全反过来。

改成在 `window` 上插一个标记：真刷新会换掉整个 document，标记随之消失。

```js
const didReload = async (action) => {
  await page.evaluate(() => { window.__mark = 1; });
  await action();
  await page.waitForTimeout(1500);
  return !(await page.evaluate(() => window.__mark === 1));
};
```

（`cachebust.mjs` 第一版就是用 `waitForNavigation` 写的，
得出「守不住无限刷新」的错误结论，查了半天才发现是测试在骗人。）

### 8. 伪造版本号做测试时，那个假值必须是【固定的】

`cachebust.mjs` 用 `page.route` 伪造 `/health` 的 `app_version`。
第一版写成 `'NEWER-' + Date.now()`，每次请求都是新值 ——
于是刷新之后还是对不上 → 再刷 → **无限刷新**，测试直接超时。

那次翻车反倒问出了产品里一个真问题：**同一个版本必须只刷一次**。
收银机陷进无限刷新，比看到旧界面严重得多。现在 `pad.js` 用
`sessionStorage` 记住「已经为哪个版本刷过了」。

### 9. 同一个 context 里，CP 与 Pad 共用会话

两边用的是同一个 `vip_session` cookie。所以在同一个 browser context 里
先登了 CP，再打开 Pad 页面时**已经是登录态**了 ——
再去 `fill('#login-name')` 会对着不可见的输入框干等 30 秒然后超时。

要么按实际状态判断：

```js
if (await pad.locator('#view-login.active').count() > 0) { /* 才去登录 */ }
```

要么给 Pad 用一个新的 context。

### 10. 用模拟活单的脚本，别让「找单窗口」把自己卡死

`tests/sim/inject_live.php` 注入的活单是按「几分钟前结账」铺开的
（3、6、9 …… 30 分钟前），而找单默认只看最近 **30 分钟**。
注入之后过 12 分钟再跑，后面那几张就找不到了 ——
脚本会挂在 `waitForSelector('#step-order.active, #step-mode.active')` 上超时，
错得**完全不像**一个时间问题。

三条都要做：

1. 脚本开头把窗口调大、末尾还原（窗口本来就是店家可调的配置）：

```js
const WIN0 = php(`... echo (new Vip\\App($c))->cfg()->get('order_lookup_window_min', '30');`);
setCfg('order_lookup_window_min', 180);
// …… 跑完
setCfg('order_lookup_window_min', WIN0);
```

2. 挑单**按 `desc` 里的说明挑**，别写死桌号，也别只看金额。
   要测计次就必须挑【计次份数 ≥ 2】的单：份数为 0 的单跑出来全程 0 次，
   而那和「规则生效了」长得一模一样 —— 是个假的绿。
   当前夹具里份数够用的是桌 40（10 份）、桌 9（6 份）、桌 10（4 份）。

3. 不同脚本别抢同一张单：提交会把订单额度分掉，
   下一个脚本再去记就只剩零头，断言会以一种莫名其妙的方式挂掉。
