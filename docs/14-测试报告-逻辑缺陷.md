## 2. 两条只修了一半的

### F9 · 服务端对了，但 Pad 还是会在客人面前被拒

座位上限现在把用券那位算回来了（`seatCap = 净份数 + 本单核销张数`），
`too_many_members` 确实不再出现。**但 Pad 在核销成功后只刷新券那一格**
（`pad.js:1341` 仍然只调 `loadRewardSlot()`，不重新 locate、不重算分摊），
于是屏幕上还是核销前算好的「4 人各 1 份」：

```
① locate      → Pad 显示「可分份数 4」，每人固定 1 份
② /points/split → [1,1,1,1]
③ 客人这时掏出券，收银员当场核销 → 净份数 4 → 3
④ 按屏幕上的数字提交
   → {"ok":false,"error":"exceeds_portions"}      整笔拒绝
⑤ 如果让页面重算一次 → [1,1,1,0] → 提交通过，用券那位计次 0   ✓
```

补救办法存在（⑤），只是**界面不会自己做**。对收银员来说，
错误从「这张单最多只能记 3 位」变成了「分配份数超过订单套餐份数」——
话换了一句，客人还是站在柜台前。

而且返回的 `detail` 里只有金额（`total` / `allocated` / `requested` 三个都是钱），
份数一个字都没有，前端就算想把话说清楚也没有材料。

**建议**：`redeemCoupon()` 成功后重新拉一次订单上下文并重算分摊，
把用券那位的份数框置 0 并标注「这一位是用券免单的，不参与分摊」；
`grantOne` 的 `exceeds_portions` 分支把 `portions` 相关的数也带进 `detail`。

### F12 · 还剩两处没兜底的 `mb_substr`

`ConfigSchema` 改用 `stripos` 了，`CardRepo` 也换了写法，但：

| 位置 | 什么时候会炸 |
|---|---|
| `bin/init.php:403` | `repair` 的**本地库连不上**那一支。而扩展检查（1/5 步）只 `bad()` 报一句、**不退出**，所以「Windows 没装 mbstring」+「库还没起来」同时成立时，`repair` 会在这里抛 `Call to undefined function mb_substr()` —— 它本来要打印的正是「MySQL 服务没起，Windows 请到服务管理器启动」那句 |
| `bin/cron.php:207` | `status` 任务打印告警摘要时 |

两处都照 `AlertRepo::raise()` 的写法加 `function_exists('mb_substr')` 兜一下即可。

## N1 🔴 P0 · POS 一断线，收银台不是降级，是整个不能用

**这一条跟本次更新无关 —— 它一直都在，是我上一轮漏掉的**（上一轮没打 HTTP 层）。

`PosDb` 的两处错误处理写的都是「返回 false 就抛 `PosUnavailable`」：

```php
$ok = @$m->real_connect(...);          // PosDb.php:44
if (!$ok) { throw new PosUnavailable('POS 主库连接失败: ' . $m->connect_error); }
...
if (!$st->execute()) { throw new PosUnavailable('POS 查询失败/超时: ' . $err); }
```

**PHP 8.1 起 mysqli 默认就是抛异常的**（`MYSQLI_REPORT_ERROR|MYSQLI_REPORT_STRICT`），
全仓库也没有任何一处 `mysqli_report()` 把它改回来。而 `@` 压得住 warning，
压不住异常 —— 于是 `real_connect` / `execute` 直接抛 `mysqli_sql_exception`，
上面那两句 `throw new PosUnavailable` 是**死代码**，一次都执行不到。
部署手册要求的正是 PHP **8.2+**（`06` §2、`bin/init.php:56`），所以线上必然是这个行为。

实测（`PosReader` 打一台连不上的主机）：

```
① 连不上的主机   → mysqli_sql_exception : Connection timed out
② 端口开着不应答 → mysqli_sql_exception : MySQL server has gone away
```

**后果是一整条链**：

```
POS 断线
 → PointsService::locate() 的 catch (PosUnavailable) 抓不到
 → 冒到 Api 顶层 → HTTP 500  server_error  E209-xxxx
 → Pad 只在 error === 'pos_unavailable' 时才显示手工录入入口
   （pad.js:584 与 :633）
 → 【收银员根本看不到那个按钮】
```

实测打真实接口（POS 不可达）：

```
POST /order/locate          → HTTP 500  {"error":"server_error","ref":"E209-3C3BBF"}
POST /order/locate-invoice  → HTTP 500  {"error":"server_error","ref":"E209-69BD67"}
POST /points/manual         → HTTP 404  member_not_found   ← 接口本身好好的
GET  /health                → "POS 主库暂时无法访问，收银流程可继续（手工录入）"
```

最后那一行是这条缺陷最难受的地方：**`/health` 说得对，柜台上做不到。**
`/health` 用的是 `catch (\Throwable)`，所以它照常判出「POS 不可达」；
而收银流程用的是 `catch (PosUnavailable)`，抓不到。同一件事，两个答案。

顺带受影响的还有两条 Cron 路径：`SyncService::incremental()` 与
`ReconcileService::verifyAmounts()` 的 `catch (PosUnavailable)` 同样落空 ——
`pos_unreachable` 告警不会挂、水位线的 `touch(…, 3, …)` 不会记，整轮直接异常退出。

> 📌 这也解释了本轮 `tests/http_sweep.php` 的 11 条失败：全部集中在
> `/order/locate` 与 `/order/locate-invoice`，全部是 500。
> 探针自己的铁律①写着「无论给什么参数都不能 500」—— 只是 POS 断线不是一个「参数」，
> 所以这条铁律没能罩住它。

**建议**：在 `PosDb::conn()` 里把 mysqli 的报错模式显式定下来
（`mysqli_report(MYSQLI_REPORT_OFF)` 后自己判返回值，或保持异常模式并
`try { … } catch (\mysqli_sql_exception $e) { throw new PosUnavailable(…); }`），
两处都要。**后者更稳**：以后 PHP 再改默认值也不会把这条防线悄悄关掉。
另外 `tests/http_sweep.php` 值得加一档「POS 不可达」的跑法
（配置里把 POS 指向一个黑洞地址），把这条铁律真正钉住。

## N2 🟠 P1 · 修了 F6 之后，同一顿饭跨「格子」边界会算两次

F6 的修法是给餐期之间的空档也编上格子，同格算一顿、跨格算两顿。
方向是对的，但它把**边界两侧**也判成了两顿 —— 而一顿饭分两次结账
（吃完加点甜点酒水另开一单）正是 `03` §3.7 专门为之写过一节的日常场景。

实测（出厂餐期 11:00–18:00 / 19:30–02:00）：

```
17:50 + 17:58   同在午市格         → 计次 1   ✓ 对照组
17:55 + 18:05   跨 18:00 边界      → 计次 2   🔴 同一顿算了两次
19:20 + 19:35   跨 19:30 边界      → 计次 2   🔴
18:10 + 18:50   同在空档格         → 计次 1   ✓ 对照组
13:00 + 21:00   午市 + 晚市        → 计次 2   ✓ 本来就是两顿
```

方向与 F6 **正好相反**：F6 是客人少拿，这一条是**餐厅多送**。
客人攒「十送一」的速度变快，而且和 F6 一样是静默的 —— 账面上每一笔都对。

顺带还削弱了另一道闸门：`max_grants_per_period`（每餐期记账次数上限）
走的是同一个 `sameSitting()`，跨一次边界就等于把这个上限重置一遍。

**建议**：「同一顿」不要只看格子相等，加一条时间邻近：
同一营业日 **且**（同格 **或** 两张单的结账时间相差 ≤ `merge_span_minutes`）。
这个参数（出厂 60 分钟）本来就是店家用来界定「这几张单是不是同一顿饭」的，
`checkMergeSpan()` 已经在用它当承重墙，两处口径统一反而更好解释。

<a id="n3"></a>
## N3 🟡 P2 · `verify_recheck_hours` 没有和保护期挂上关系

F1 的修法把复查间隔做成了后台可配（出厂 168 小时 = 7 天），
但 `ConfigSchema` 只校验它是正整数，**不看它和 `verify_protect_days`（出厂 30 天）的关系**。
填一个大于 720 小时的数，每张单在保护期内就只会被比对一次 —— F1 原样回来，
而且和当初一样静默：界面不报错，告警不响，值比对每晚照常「跑完」。

顺带一提，出厂 168 小时意味着 POS 侧的改单**最长 7 天后才会被发现**，
比 `03` §7.3 写的「保护期内每次校准任务执行」宽了一档。
这是有意的负载取舍（代码注释里算过账），但**文档那一行该跟着改**，
否则下一个人按文档去核对会以为哪里坏了。

**建议**：保存时若 `verify_recheck_hours × 3600 > verify_protect_days × 86400 ÷ 2`
就拒绝或至少挂一条告警；`03` §7.3 那张表把「每次校准」改成「每 N 小时，N 可配」。

<a id="n4"></a>
## N4 🟡 P2 · 「待发」名单每次都要把全部会员捞进 PHP 里算一遍

`pendingList()` 与 `pendingAcrossMembers()` 都是
`SELECT … FROM member LEFT JOIN card` **全表**，再在 PHP 里逐个算 `progress`。
而它们被调用得不算少：

| 触发 | 次数 |
|---|---|
| 后台打开「奖励券」页 | 每次 1 遍 |
| `/config/save` 保存任意一项配置 | **2 遍**（护栏前后各量一次） |
| `/tiers/save` 保存等级 | **2 遍** |

单店几千名会员时无所谓；会员上万之后，后台改一个开关要扫两遍全表。
不是正确性问题，但值得在会员量涨上去之前先记一笔。

**建议**：待发张数能用一条 SQL 算出来（`FLOOR(进度/门槛) - rewards_issued`，
按 `tier_code` 分组），只有需要明细列表时才回 PHP。

<a id="n5"></a>
## N5 🟡 观察 · 用券的人不在这一单上、而这一单还有份数在付费时，只告警不冲正

`clawBackVisitOnRedeem()` 分三档：净份数归零 → 退所有人；`by_portion` → 按总量退；
其余情况 → **只动券持有人**。所以当「券持有人不在这一单的记账人里，
而这一单还剩付费份数」时，多出来的那一次退不掉，挂一条
`redeem_visit_unattributable` 告警（severity 2）了事。

这是代码里写明的取舍（「不猜」），我同意在这一档不猜。
只是要说清楚：**这一档下餐厅仍然实打实少收一次的成本**，
靠的是有人每周去看那条告警。`13` §6 的影子模式建议应当把这条告警也列进去。

## 2. P0 —— 会直接产生餐费损失或毁掉客人权益

<a id="f1"></a>
### F1 · 值比对每张单只跑一次，30 天保护期形同虚设

**文档说的是**（`03` §7.3）：

| 项 | 建议值 |
|---|---|
| 值比对保护期 | 发分后 30 天 |
| 保护期内回读频率 | **每次校准任务执行** |

容量估算也是照这个算的：「保护期内待比对订单量 30 天 × 95.6 单/天 ≈ **2,870 单** → `LIMIT 100` 分 29 批」。

**实际是**：`ReconcileService::verifyOne()` 一发现金额一致就
`markVerified($serial, 1)`（`ReconcileService.php:140`），
而 `OrderRepo::pendingVerify()` 只取 `verify_status = 0`（`OrderRepo.php:265`）——
**全仓库没有任何地方把它改回 0**。于是每张单只在「记账后的第一个夜里」被回读一次，
之后永久退出视野。真实的每晚待比对量是 ~96 单（1 批），不是 2,870 单（29 批）。

**实测**：

```
第 1 晚  值比对 {"checked":1,"changed":0}      verify_status → 1
第 2 天  POS 把这单从 50.00 改成 10.00
第 2 晚  值比对 {"checked":0,"changed":0}      ← 根本没看它
         会员积分仍然是 50
```

**代价**：主库实测 **2,569 单（2.9%）在结账后被改过，其中 1,144 单晚于结账 30 分钟以上**
（`01` §2 `edit_time`）。这些改动只要没赶上「记账当晚」那一次，积分、计次、
以及由计次换来的**免费餐券**就永远不会被退回。

**建议**：`pendingVerify` 的条件改成「保护期内 且（未核对过 或 距上次核对 ≥ 1 天）」，
即 `verify_status IN (0,1) AND (last_verified_at IS NULL OR last_verified_at < ?)`；
`markVerified(…, 1)` 保留但只当作「上一次核对一致」，不再当作终态。
`verify_status = 2/3`（已冲正 / 待人工）仍是终态。

<a id="f2"></a>
### F2 · 值比对的「快照」根本不是快照 —— 再查一次单就把基准冲掉了

`verifyOne()` 拿来比对的「发分时快照」是 `pos_order.should_amount / actual_amount`
（`ReconcileService.php:136-142`）。但这两列同时也在 `OrderRepo::upsert()` 的
**「两边都写」那一份**里（`OrderRepo.php:62-66`），于是有两条路会把它改成 POS 的当下值：

| 谁 | 什么时候 |
|---|---|
| `PointsService::buildContext()`（`PointsService.php:302`，`$computed = true`） | **每一次 locate** —— 包括为第二位客人再调一次单 |
| `SyncService::storeOrder()`（`SyncService.php:206`，`$computed = false`） | 每 20 分钟一轮，覆盖近一轮内结账的单 |

比对的基准被改成了「和 POS 一样」，比对当然判「一致」。

**实测 A —— 再 locate 一次**（AA 只记了部分人，客人补卡是天天有的操作）：

```
记账      71.70 → 71 分、计次 1
POS 侧    整单作废（0.00）
收银员    为第二位客人再 locate 一次  ← 正常操作
夜间比对  {"checked":1,"changed":0}   ← 判「一致」
结果      积分 71、计次 1 一分没退
镜像      total_amount = 0.00 而 allocated_amount = 71.70   ← 自相矛盾
```

最后那一行正是 `smoke ⑬`「没有任何订单的已分配额超过可积分总额」要挡的形状 ——
这条不变量在生产里是会被破坏的，只是冒烟测试造不出这个顺序。

**实测 B —— 撞上一轮增量补抓**（结账后当场改单，比 A 更常见）：

```
记账      60.00 → 60 分
8 分钟后  POS 上退掉一道菜  60.00 → 30.00
20 分钟   增量补抓把镜像 should_amount 改成 30.00
夜间比对  {"checked":1,"changed":0}
结果      60 分一分没退
```

**根因与 `03` §3.9 是同一处**：那次修复给「要算的列」（份数、排除项、核销）加了
`$computed` 开关，并留下一条规矩「POS 直接给的（should/actual/tax…）放进两边都写的那份」——
而**恰恰是这几列在当比对基准**。规矩本身把洞留在了原处。

**建议**：给 `pos_order` 加一组只在**首次发分那一刻**写入、之后任何人都不再更新的
快照列（`snap_should_amount` / `snap_actual_amount` / `snap_total_amount`），
`verifyOne()` 只认它。`should/actual` 继续跟随 POS 当下值（报表要用），两者分开。

<a id="f3"></a>
### F3 · 换过发券口径之后，一次撤销把客人手上的券全部作废

`coupon.progress_at_grant` 存的是**发券当时那个口径**的进度：
按次数口径下是「次」，按金额口径下是「分」（`RewardService::issue()`）。
而 `clawBackOverIssued()` 拿它直接跟**当下口径**的 progress 比大小
（`RewardService.php:667`：`AND progress_at_grant > ?`）—— 两个数不是同一个单位。

**实测（按金额 → 按次数）**：

```
按金额口径（门槛 50.00）消费 180.00  →  3 张券，progress_at_grant = 6000 / 12000 / 18000
店家改回按次数（门槛 10 次）        →  progress = 3（次）
经理撤销其中一笔（记错卡）          →  6000 > 3、12000 > 3、18000 > 3  全部命中
结果：3 张券 status 全部变成 4（已作废），一条告警都没有
```

作废的券**不会复活，经理 force 也核销不掉**（状态检查排在 force 分支之前，`13` §1.2）。
客人下次拿券来吃饭，屏幕上就是「此券已作废」，谁也解释不了。

**反方向（按次数 → 按金额）同样错，只是错法相反**：券一张都收不回来，
却挂了一条 `reward_on_reversed_grant`「由它带出的 1 张免费餐券【已经被核销】，收不回来了」——
**告警是假的**，经理照着它去查一顿根本没被吃掉的免费餐。

`ReconcileService::applyShrink()` 走同一个方法，所以 POS 侧改单也会触发。

**建议**：`coupon` 加一列 `progress_mode`（`visits` / `amount`）；
`clawBackOverIssued()` 只在「券的口径 == 当下口径」时才按进度定位，
口径不同的券一律不动（它们是按另一套规则挣到的，本来就不该被这次撤销牵连）。

<a id="f4"></a>
### F4 · 先记账、后核销 —— 用券吃的那一餐又攒了一次

`redeem()` 会把「这一单是用券吃的」写回订单（`OrderRepo::markRedeemedByApp()`，
`03` §6.3ter 那次修复），但它**只改订单镜像，不回头看已经写进去的流水**。

**实测**：

```
4 人同桌 95.60 / 4 份，收银员先按 AA 记账 → A、B 各 1 次
记完之后 A 才想起来自己有免费餐券 → 核销（带单号）
结果：订单 is_redeemed = 1、净份数 4 → 3
      而 A 的 visit_count 仍然是 1   ← 他既吃了免费餐，又攒了一次
```

`redeem_unflagged` 那条对账告警**抓不到**：订单确实被标成核销了，`unflagged = 0`。
全程静默。

这就是 `03` §6.3ter 描述的「免费餐自己在为下一顿免费餐攒进度」，
只是走的不是「匹配串失配」那扇门，而是**操作顺序**那扇门 ——
而 Pad 上核销按钮就挂在分配页每位会员下方，先记后核完全是自然操作，
客人吃完才掏券更是常态。

**建议**：`redeem()` 带了单号时，在同一笔事务里把该单上**这位会员**的有效流水
`counted_visit` 冲掉（写一条 `T_REFUND` 的 `counted_visit = -1` 并同步 `member.visit_count`），
并顺手调一次 `clawBackOverIssued()`。要么就在 Pad 上把「核销」挪到提交之前的必经步骤。

<a id="f5"></a>
### F5 · 券与卡的有效期按【日历日】判，而营业日到次日 02:00

三处都是同一个写法：

| 位置 | 代码 |
|---|---|
| `RewardService::redeem()` `:506` | `$c['valid_to'] < date('Y-m-d')` |
| `RewardService::expireStale()` `:460` | `valid_to < ?` ← `date('Y-m-d')` |
| `CardRepo::isExpired()` `:257` | `$v < ($today ?? date('Y-m-d'))` |

而这家店的晚市餐期是 **19:30 – 次日 02:00**，`03` §5.1 自己写着
「**00:xx 发券是这家店的常态**，不是边角」。

**实测**：

```
券上印着 2026-09-02 到期
客人 2026-09-02 晚上 23:50 入座，00:20 结账时拿券出来
→ redeem() 返回 coupon_expired
→ 并且顺手把券 status 改成 3（已过期）
→ 之后经理 force 核销也不行：coupon_not_active（状态检查排在 force 之前）
```

更早一步就已经死了：服务员只要在 Pad 上点开这位客人，
`/member/rewards` → `availableFor()` → `expireStale()` 就把券改成已过期了 ——
**「查一下有没有券」这个动作本身会把券作废**。

卡也一样：卡面写着 X 日到期，客人在 X 日的晚市来扫卡 → `card_expired`。
（卡这一侧代价小些，换卡能把积分/计次/券全部结转，但客人被告知「卡过期了」时
卡面上明明写着今天。）

与 `11` 立的规矩「**券面/卡面上印的日子就是最终的日子**」正相反 ——
`03` §5.1 刚为了同一句承诺修掉过「跨夏令时差一天」，这次差的是**跨零点的那 2 小时**。

**建议**：判过期一律用「当前营业日」而不是日历日 ——
`$today = $bizDay->of(date('Y-m-d H:i:s'))`，三处都换。
`expireStale()` 同理（它比 `redeem()` 更危险：它会**改状态**）。

## 3. P1 —— 客人当面吃亏，而且自己发现不了

<a id="f6"></a>
### F6 · 餐期之间留了空档，落在空档里的那一顿把一整天算成同一顿

出厂种子（`db/seeds/002_meal_period.sql`）配的是 **11:00–18:00** 与 **19:30–02:00**，
中间空着 90 分钟。`MealPeriod::of()` 对这段返回 `null`，
而 `sameSitting()` 一旦有一边是 null 就**退回「同一营业日」这个更粗的口径**
（`MealPeriod.php:97-101`）。

**实测**（同一天来了三顿）：

```
13:30 午市   → 计次 1
18:30 空档   → 计次 0     ← 被判成和午市「同一顿」
21:00 晚市   → 计次 1
这一天他来了 3 顿，最终计次 = 2
```

顺序反过来（先 18:30 再 21:00）则是**晚市那顿丢掉**。无论怎么排，
只要有一单落在空档里，那一天就少 1 次。

对照组（13:30 + 21:00，都在餐期内）= 2 次，正确。

**没有任何地方会报**：`Features::warnings()` 的 `meal_period_missing`
只在「一个餐期都没配」时才挂红条（`Features.php:56`），
配了但留空档一句话都没有。客人要等到攒够十次那天才发现少了几次，
那时已经查不了 —— 正是 `13` §3.1 那张表里「静默少给」的形状。

**建议**：两件事一起做 ——
① `Features::warnings()` 增加一条「餐期覆盖有空档」的检查（把配好的区间并起来，
   报出未覆盖且历史上有订单的时段）；
② `sameSitting()` 里当**只有一边**落在餐期外时不要退回「同一营业日」，
   而应判否（两顿不同的饭），退回粗口径只在**两边都** null 时才有意义。

<a id="f7"></a>
### F7 · 手工录入不触发发券，而屏幕上还写着「还差 X」

`/points/grant` 与 `/points/grant-merged` 记完账都会调 `checkAndGrant()`
（`api/routes.php:825`、`:874`），**`/points/manual` 与 `PointsService::manualGrant()` 都没有**。

**实测**（按金额口径、门槛 100.00）：

```
手工录入 150.00  →  {"ok":true,"points":150}
进度            →  {"progress":15000,"earned":1,"issued":0,"pending":1}
券表            →  0 张
Pad 上那句话    →  「已累计 € 150.00 / 每 € 100.00 送 1 次，还差 € 50.00」
```

客人已经挣到一张券了，屏幕上却告诉他**还差 50 欧**
（`progressOf()` 的 `remain = (earned+1)*threshold - progress`，
它假设 earned 那几张已经发出去了）。

券不会永久丢失（下一次正常记账会补上），但：
* 客人当场拿不到，而 POS 挂掉那一天恰恰是最需要给点补偿的时候；
* `reward_from_manual_entry` 这条告警写在 `checkAndGrant()` 里面，
  所以「靠打字凑出一顿免费餐」的那一刻**也不会留痕** ——
  与 `03` §10.3「造出免费餐的那一刻永远不是静默的」正相反。

**建议**：`/points/manual` 成功后照 `/points/grant` 的样子调一次 `checkAndGrant()`；
另外 `progressText()` 在 `pending > 0` 时该换一句话（「已达标，待发 N 张」），
不能继续说「还差多少」。

### F8 · 文档推荐的「影子模式」在后台没有落地

`03`/`13` §6 建议上线第一个月：

> `reward_auto_grant = 0` 自动发券关掉 ——
> 达标的客人**进后台「待发」队列**，由经理逐张确认后发出。

**这个队列不存在。** 逐个接口查过：

**建议**：后台首页加一个「待发券」计数 + 一个可点进去的列表
（`SELECT` 全部会员按各自等级门槛算 `pending`，`pendingAcrossMembers()` 已经有这套算法了，
拆一个返回明细的版本即可），列表里每行一个「发放」按钮走 `grantManual`。
在做出来之前，`06` 与 `13` 里那句上线建议应当先撤掉或改写。

### F9 · 客人中途掏出券 → 按屏幕上的数字提交，被 `too_many_members` 当面拒掉

核销会把订单的 `portions_counted` 减 1（`OrderRepo::markRedeemedByApp()`），
而 `grantOne()` 的座位上限 `seatCap = max(1, $totalPort)` 直接吃这个数。
Pad 分配页的上下文却是**核销之前** locate 出来的，
`redeemCoupon()` 成功后只调 `loadRewardSlot()` 刷新券那一格
（`pad.js:1341`），**不重新 locate**。

**实测**：

```
4 人单（4 份），locate 后 Pad 显示「可分份数 4」
收银员当场给 A 核销了一张券
按界面上算好的 4 人 AA 提交
→ {"ok":false,"error":"too_many_members","detail":{"cap":3,"requested":4}}
```

（口径本身没错：`03` §5.5 说的就是「4 人 1 人用券 = 算 3 份，AA 给那 3 个人」。
错的是**界面没跟着变**，把一个可预期的状态变化变成了柜台上的一次拒绝。）

**建议**：`redeemCoupon()` 成功后重新拉一次订单上下文并重算分配
（顺带把 A 从人数里去掉、把提示写成「这一位是用券免单的，不参与分摊」）。

<a id="f12"></a>
### F12 · `ConfigSchema` 里用了没有兜底的 `mb_strtoupper()`

`ConfigSchema.php:549`（`checkRedeemPatterns()`）——
而 `PointsEngine::isRedeemLine()` 的注释与 `AlertRepo::raise()` 的 `function_exists('mb_substr')`
兜底都是为了同一件事写的：**现场 Windows 上没开 mbstring**。

于是那种机器上保存 `redeem_line_patterns` 会直接 500 ——
而这恰恰是「店家改了 POS 折扣行名称之后必须改的那一项」。
`bin/init.php:403` 与 `bin/cron.php:174` 同样无兜底
（诊断工具在报告这类错误时自己也会崩）。
典型的 `13` §3.1「修了那一处，没修那一类」。

<a id="f13"></a>
### F13 · 「白送了一顿饭」的告警按会员去重，第二次不会再报

`reward_on_reversed_grant` / `reward_on_shrunk_order` 都走
`raiseOnce($type, 'member', $memberId, …)`。同一位会员的第二次损失，
在第一条告警被处理之前**不会产生新记录**，而告警正文里写死了具体单号 ——
经理按着第一条去查，第二笔就没了。这类告警的去重键该带上单号。

<a id="f14"></a>
### F14 · 手工录入日累计上限的检查在事务外

`manualGrant()` 里 `manualAmountSince()` 的判断在 `db->transaction()` **之前**
（`PointsService.php:1589`），两笔并发录入可以同时读到「还没到顶」。
上限本身的设计（`03` §10.3「超了经理也不能放行」）是对的，
但它挡不住两台 Pad 同时提交。建议把校验挪进事务、并先锁会员或操作员行。

<a id="f15"></a>
### F15 · 小票回溯天数用 `N × 86400` 秒

`PointsService::locateByInvoice()` `:144`：
`strtotime($this->pos->now()) - $maxDays * 86400`。
跨夏令时那两天会差一小时。影响很小（7 天窗口的边界差一小时），
但 `13` §3.3 刚刚为了同一个写法修掉过券的到期日，
这里是同一类里剩下的一处。改成 `->modify("-{$maxDays} days")` 即可。

## 5. 查过、没有问题的部分

写出来是为了让「没被提到」不等于「没查」：

| 查了什么 | 结论 |
|---|---|
| 金额守恒（`exceeds_total` / `exceeds_portions`） | 正确，事务内以镜像为准，不信客户端 |
| 「份数必须带金额」「一分钱不能换一次」 | 正确，且 `× 份数` 那一乘确实在 |
| 同一张卡在同一张单上记两次 | 两层都在（`duplicate_member` / `member_already_on_order`） |
| 撤销 → 同一餐期重打 | 正常计次（原流水被标 REVERSED，退出风控视野） |
| 整单归零 → 计次与积分退回 | 正确（多人单两位都退了） |
| 固定加锁顺序防死锁 | `smoke ㊱` 在 MariaDB 上 100/100 通过，0 次死锁 |
| 并发发券只发该发的张数 | `smoke ㉖` 通过（行锁 + 事务） |
| `alloc_status` 依赖的「UPDATE 从左到右求值」 | 在 MariaDB 10.11 上实测成立 |
| 核销额反推免费份数（`redeemedPortions`） | 两级判据都只会**多算**免费份数、少给计次，方向安全 |
| 定点乘除（`fixedFloor`）少一分 | 正确，穷举无偏差 |
| 券有效期跨夏令时 | 正确（`expiryDate()` 走日历天） |
| 无 PII 会员会不会被合规任务假名化 | 不会（`$hasPii ? PENDING : ACTIVE`） |
| 换卡后等级/券/计次结转 | 正确（旧卡 `member_id` 置空，唯一键保证一人一卡） |
