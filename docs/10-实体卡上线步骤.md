# 10 · 实体卡上线步骤

> 从当前版本升级到「实体卡」版本，照着做即可。
> 背景与设计理由见 [`09-实体卡.md`](./09-实体卡.md)。

## 零、这次改动会影响什么

| 影响面 | 说明 |
|---|---|
| **数据库** | 新增一张 `card` 表。**不动任何现有表**，已有数据不受影响 |
| **配置** | 新增一项 `card_prefix` |
| **Pad 端** | 建会员**必须先扫卡**，不扫卡会提示「请先扫描客人的实体会员卡」 |
| **后台** | 新增「发卡」标签页 |
| **兑换** | 核销免费餐券**必须验卡背 PIN**（经理可强制核销） |

> ⚠️ **升级后到拿到实体卡之前，无法新建会员** —— 建会员必须先有一张
> 库存里的实体卡。已有会员的积分、计次、券全部照常可用。
> 空窗期不可接受的话，先在后台生成一批卡、手工抄几张卡号应急。

> ℹ️ **建会员不需要问客人任何个人信息** —— 扫卡、点「启用这张卡」，完事。
> 详见 §10。

## 一、更新代码

整体替换这四个目录：`wwwroot/` `app/` `bin/` `db/`。

**不要挑着传** —— 这次跨了多个提交，漏一个文件的表现往往是「某个功能静默失效」
而不是报错。

传完在服务器上核对：

```bash
cd /www/wwwroot/lms.sushisom.org/www
php -l app/lib/CardNumber.php && echo "CardNumber OK"
php -l app/lib/Repo/CardRepo.php && echo "CardRepo OK"
php -l app/lib/Service/CardService.php && echo "CardService OK"
ls -1 db/migrations/ | tail -3
```

最后一条应该看到 `006_card.sql`。

## 二、加配置项

编辑 `app/config/config.php`，在 `store_name` 后面加一行：

```php
'card_prefix' => 'TK',        // 1~4 位字母，印在卡号最前面
```

前缀会印在每张卡上，**印过卡之后不要再改** —— 改了新旧卡前缀不一致，
盘点和手输都会乱。

> 这一版**不需要任何密钥**。早期设计里有个 `card_hmac_secret`，已经去掉了：
> 卡号无论如何都要查库，离线验证没有价值，而那个密钥丢了会让全部实体卡作废。

```bash
php bin/init.php migrate
```

期望输出：

  ✓ 014_grant_group.sql

| 迁移 | 做什么 |
|---|---|
| `006` | 新建 `card` 表 |
| `007` | 给 `member` 加几个确认码字段 |
| `008` | 给 `card` 加 `valid_to` / `points_cleared_at` 两列和一个索引 |
| `009` | 给 `operator` 加 `lang` 一列（界面语言，见 [`12-多语言.md`](./12-多语言.md)） |
| `010` | 给 `operator` 加 `display_name_es` 一列（西语显示名，同上） |
| `011` | 新建 `card_tier` 表，给 `card` 加 `tier_code`，给 `point_ledger` 加 `tier_code` / `tier_multiplier`（卡片等级，见 [`09`](./09-实体卡.md) §10） |
| `012` | 给 `card_tier` 加两个送 1 门槛，给 `coupon` 加 `tier_code` / `threshold_used`（按等级的奖励，同上 §10.6） |
| `013` | 给 `card_tier` 加 `coupon_valid_days` 一列（按等级的券有效期，同上 §10.7） |
| `014` | 给 `point_ledger` 加 `grant_group` 一列和一个索引（多桌合并记账，见 [`03`](./03-积分与防刷引擎.md) §12） |

**九条都不碰任何现有数据**，在有数据的库上实测通过。
迁移是**累加**的：老库直接跑 `migrate` 即可，不需要删库重建。

如果报「拒绝执行：…含 DROP TABLE」，说明代码没传全（`app/lib/SqlText.php` 漏了）。

> ⚠️ **跑完必须自检一次**：`php bin/init.php check`。
> 这条命令早期版本硬编码了 10 张表的名单，`card` 建出来了它也不报 ——
> 于是「✓ 全部 10 张表已存在」和「后台发卡点了没反应」同时成立。
> 现在名单已改为跟着迁移走，但**看输出时仍要数一下表的张数对不对**。

## 五、生成第一批卡

后台 → **发卡** 标签页 → 「生成新批次」。

### 5.0bis 要不要用卡片等级

**不用就跳过这一节** —— 发卡时选「不分级」，界面上不会出现任何与等级相关的东西。

要用的话先去 **后台 → 发卡 → 卡片等级** 把等级定好
（名称、积分倍率、几次送 1 次、券有效期），再回来发卡。等级**整批统一**，印刷清单会多一列供印刷厂排版。

> 等级属于卡不属于会员 —— 想给客人升级就是发一张新卡给他。
> 改倍率只影响以后的入账，历史流水一行都不会变。详见 [`09`](./09-实体卡.md) §10。

### 5.0 🔴 先决定有效期

**有效期是必填项，而且要先想清楚再点。**

- **已经默认填好「2 年后的 12 月 31 日」** —— 只是预填，改成别的照填不误
  （包括更早的日期；系统只拦「今天或更早」，别的一律放行）
- 取年底是因为卡面上印「12-31」比印「03-17」好记好核对，
  整批卡的作废时间也集中，不会一年到头零零散散地过期
- 日期右边有一行红字写着**距今多少天**（如「距今 855 天，约 2 年 4 个月」），
  改一下就跟着变
- 填完会**单独弹一次确认**让你核对这个日期，那行红字也会再出现一次 ——
  因为它要印在卡面上，印错就是整批重印

> **为什么要那行天数。** 日期本身「对不对」是看不出来的 ——
> 2028 还是 2029，盯着看也就那样。换算成天数就不一样了：
> 记错一年，数字差出三四百天；年份多打一位，从「约 2 年」变成「约 12 年」，
> 一眼就不对。它挡的是**人一时反应错**，不是数据格式错。

法规依据、卡面文案与店内告示 → [`11-卡片有效期与告知.md`](./11-卡片有效期与告知.md)。

> 有效期是**逐张**存进 `card.valid_to` 的。
> 这意味着以后改规则只影响新批次，**已经发出去的卡不受影响** ——
> 这是刻意设计，不要试图批量改老卡的有效期（11 §4.2）。

### 5.1 先印 5~10 张试样

不要一上来就批量下单。先生成 10 张，拿去跟印刷厂对格式，确认无误再下大单。

### 5.2 🔴 生成后立刻复制清单

界面会一次性显示全部卡号与 PIN。**这是明文 PIN 唯一出现的时刻** ——
库里只存不可还原的 hash，关掉窗口就再也取不回来，只能作废整批重新生成。

全选文本框内容复制，粘进 Excel 就是四列。

### 5.3 交给印刷厂的四个要点

| 印在哪 | 用哪一列 | 例 |
|---|---|---|
| 二维码 | 「二维码内容」列（**无连字符**） | `TK00000001KWQ` |
| 卡面文字 | 「卡号」列（**带连字符**，便于念和手输） | `TK-00000001-KWQ` |
| 卡面日期 | 「有效期至」列 | `Válida hasta 31/12/2028` |
| 卡背刮开层下 | 「PIN」列 | `871809` |

**PIN 必须在刮开层下面，不能露在外面。**

**日期字号不得小于卡号**，且必须是印刷内容（不是手写、不是贴纸）。
卡背还要加一段小字说明换卡规则 —— 逐字文案见
[`11-卡片有效期与告知.md`](./11-卡片有效期与告知.md) §6.1。

### 5.4 清单用完即销毁

那份 Excel 是全部卡的总钥匙。交给印刷厂、印完确认后就删掉，
不要留在邮箱、网盘或聊天记录里。

## 六、Pad 端更新（现在会自己来）

**不用再去点刷新了。** 页面已经改成由 PHP 发（`index.php`），
资源 URL 带着版本号，Pad 会自己发现有新版本并在**安全时机**刷掉：
停在第一步、或一单做完点「下一单」的时候。

所以正常节奏是：**传完文件，收银员做完手上这一单，下一单就是新版本。**

> 它绝不会在收银员填了一半时刷新 —— 已填的金额、选好的会员会当场清空。
> 机制与注意事项见 [`06-部署手册.md`](./06-部署手册.md) §4.1 / §4.2。

🔴 **第一次升到这套机制时，服务器上要做三件事**（只做这一次）：

1. nginx 的 `index` 改成 `index.php`
2. 放行 `/index.php` 与 `/cp/index.php`（否则被 `location ~ \.php$` 拦掉，
   **站点直接打不开**）
3. **删掉服务器上旧的** `wwwroot/index.html` 和 `wwwroot/cp/index.html`

具体配置见 `06` §4。第 3 条最容易漏 —— 留着它服务器多半仍会优先发它，
症状和以前一模一样（改了代码不生效），极难发现。

实在要手动刷：PC 上 `Ctrl + F5`；平板上杀进程重开。

## 七、真机验一遍

拿到卡之后，在平板上：

- [ ] 会员弹层的「卡号」档能看到**扫卡**按钮
- [ ] 点扫卡能打开相机取景框（若提示「本设备不支持扫码」见下）

在 `chrome://inspect` 的 Console 里执行：

  告诉开发，可以考虑内置一份识别库。

## 八、兑换流程变了，要跟收银员交代

核销免费餐券时，Pad 会要求**输入卡背 PIN**：

```
确认核销 → 请让客人刮开卡背，报出 6 位 PIN → 核销
```

要交代给店员的三件事：

1. **PIN 在卡背刮开层下面**，第一次兑换时让客人刮开，之后自己记住
2. **连错 5 次会锁 15 分钟**，锁定期内 PIN 对了也不给过
3. **客人报不出 PIN 时找经理** —— 经理界面上会出现「强制核销」，
   填个原因就能过。收银员账号看不到这个入口

> 经理强制核销会记入审计日志（`coupon_redeem_forced`），
> 后台「审计」页按这个动作能筛出全部强制核销记录。

## 七bis、客人问「我这卡还能用吗」

**Pad 第一步（找订单）下面有个「查一张卡」。** 扫一下或输卡号，
屏幕上直接给一句能照着念的话：

| 卡的状态 | 屏幕上写什么 |
|---|---|
| 正常 | 「可以正常使用」+ 积分、消费次数、**有几张免费餐券**、有效期 |
| 快到期 | 「可以用，但还有 N 天到期 —— 建议现在就换一张，积分会全部转过去」 |
| 已过期、还在宽限期 | 「已过期，但现在换一张新卡还来得及」 |
| 过期太久 | 「积分按规则已失效。如需破例换发，请找经理」 |
| 还没启用 | 「客人下次消费时扫一下就能开通」 |
| 已作废 | 「这张卡已作废，不能再用」+ 作废原因 |

三件事要交代给店员：

1. **这是只读的** —— 查多少次都不会改动任何东西，不用怕点错
2. **不需要卡背 PIN** —— PIN 只在核销免费餐时才要
3. **屏幕上不显示客人的手机号和邮箱** —— 卡本来就是不实名的，
   查卡是为了回答「还能用吗」，不是翻客人的档案

> 后台那个查卡**仍然保留**：经理对账、处理投诉、查作废原因时要用，
> 而且后台那个会多显示批次号和联系方式。

## 八bis、卡到期了怎么办 —— 要跟收银员交代的

**一句话：卡到期不是分没了，是卡该换了。**

收银员什么都不用记，扫卡时系统会自己说话：

| Pad 上出现什么 | 收银员做什么 |
|---|---|
| 弹窗「这张卡还有 N 天到期 · 现在换卡 / 稍后再说」 | 顺口问客人要不要现在换。**忙、新卡没到、客人不想换 → 点「稍后再说」**，什么都不耽误 |
| 弹窗「此卡已过期 · XX 分 · 已消费 X 次 · 要换吗？」 | 点「换发新卡」→ 扫一张新卡 → 完事，**积分自动转过去** |
| 「此卡已过期，且从未启用过」 | 这张库存卡放过期了，**换一张发给客人**，别纠结 |
| 发卡时弹「这张卡只剩 N 天就到期了」 | **默认选「换一张」**，别把快到期的卡发出去 |
| 「已超过宽限期…请找经理操作」 | 就是字面意思：**叫经理**。收银员这边没有别的按钮 |

要交代的四件事：

1. **到期前一个月起，每次扫这张卡都会弹提醒** —— 这是故意的，不是系统坏了。
   点「稍后再说」就过去了，卡照常用。**这一个月里客人只要来过一次并换了卡，
   他的分就一分不会掉**
2. **到期后 6 个月内还能换**，积分一分不少 —— 客人拿着刚过期的卡来，
   直接给换，不要说「过期了不行」
3. **换卡免费**，任何情况下都不要收钱
4. 客人问为什么有到期日：「卡是不记名的，谁捡到谁能用，到期日对您也是保护」

### 超过宽限期的客人怎么办

过期超过 6 个月才来的，按规则积分已经失效。**但收银员不用当面回绝** ——
Pad 上会直接写着「请找经理操作」。

经理登录后同一张卡会多出「强制换发」的选项，**必须填写原因**，
确认后积分照旧全额结转。每一次都会记进审计日志，后台查得到是谁、
什么理由、哪一天放的行。

> 这条口子是给经理的判断留余地，不是让它变成常规操作。
> 收银员账号上根本看不到这个按钮。

发卡时那句话（西班牙语原文见
[`11-卡片有效期与告知.md`](./11-卡片有效期与告知.md) §6.3）：

> 「这张卡用到 [日期]。到期前拿来，免费换新卡，分都在。」

> 🔴 **绝对不要改已经发出去的卡的有效期**，也不要提前清零还在宽限期内的积分。
> 这是这套规则唯一的法律红线，理由见 11 §4.2。

## 九、日常会用到的操作

| 场景 | 在哪做 |
|---|---|
| 客人问「我这卡还能用吗」 | **Pad 第一步的「查一张卡」** —— 服务员当场就能答，不用找经理 |
| 经理要查某张卡（对账、投诉、看作废原因） | 后台 → 发卡 → 查一张卡（多显示手机号/邮箱与批次） |
| 客人的卡到期了 | **不用去后台**，Pad 扫一下就会引导换卡 |
| 客人报失/卡损坏 | 后台 → 发卡 → 挂失作废；之后到店扫一张新卡即可换发 |
| 卡快用完了 | 后台 → 发卡 → 生成新批次（顺序号自动接上一批，**有效期要重填**） |
| 看还剩多少库存 | 后台 → 发卡，顶部统计 |
| 想知道某批卡印的是哪个有效期 | 后台 → 发卡 → 批次列表，有单独一列 |
| 想调某个等级的积分倍率 | 后台 → 发卡 → 卡片等级 → 编辑。**只影响以后的入账** |
| 想让金卡少几次就送 1 次 | 同上 → 「几次送 1 次」。留空即跟随全局；**调低会当场补发，调高不会收回已发的券** |
| 某个等级不想再用了 | 同上 → 停用（别删：已发出去的卡还要显示等级名） |
| 觉得提醒来得太早/太晚 | 后台 → 配置 → **实体卡有效期** → 「提前多少天开始提醒换卡」 |
| 想放宽或收紧过期后的补救期 | 同上 → 「过期后还能换卡的宽限期」。⚠️ 收紧属于改规则，只对以后发的卡合适 |
| 查谁破例强制换过卡 | 后台 → 审计 → 动作选 `card_replace_forced` |

## 十、卡片不实名 —— 要跟店员交代的

**默认不收任何个人信息。** 扫一张新卡 → 点「启用这张卡」→ 完事，
不用问手机号、不用问姓名，客人当场就能积分。

默认状态下，Pad 上**根本没有**手机号/邮箱/生日的输入框 —— 后台开关
`member_collect_pii`（合规与隐私组）默认关闭，那一栏整块不渲染，后端也拒收。

这样收银员没有向客人索要信息的入口，门店也不必为一个没在用的采集表单
去应付「你们收了个人信息，保护措施呢」这类检查。

同理，「选择会员」弹层里的**「手机号 / 邮箱」两档也是灰的**，只剩「卡号」，
旁边写着「本店不登记手机号和邮箱，只按卡号查」。
—— 点得动就意味着收银员会开口问，客人报了系统又存不进去，双方白跑一趟。

> 要开启的话见 §11 —— 需要先在 `config.php` 里配好短信或邮件的凭据，
> 否则客人收不到确认码、积分会一直冻结（后台会一直挂红条提醒）。

### 要说清楚的三件事

| 情况 | 后果 |
|---|---|
| 客人忘带卡 | **当天积不了分**，没有别的途径找到账户 |
| 客人丢卡 | **分就没了**，捡到的人凭卡 + PIN 就能用，跟现金券一样 |
| 有人来报失 | **没法核实他是不是卡主**，挂失只能靠店员判断 |

建议在卡面或卡套上印一句「本卡遗失不补，请妥善保管」。

## 十一、要开启实名功能的话

实名（收集客人联系方式）现在**是可用的**，双重确认走**现场确认码**：
系统发一条含 6 位码的短信/邮件，客人当场报给收银员，Pad 输入即完成。

> 不是「点链接确认」—— 那需要公网可达的端点接收点击，而门店网络是单向的。
> 这个矛盾在原设计里没被发现，详见 `docs/05` §2.2。

### 11.1 开启前要配的

**① 凭据填进 `app/config/config.php`**（二选一或都配）：

```php
'sms' => [
    'driver' => 'twilio',
    'sid'    => 'ACxxxxxxxx',
    'token'  => 'xxxxxxxx',
    'from'   => '+34xxxxxxxxx',   // Twilio 上开通的号码
],
'mail' => [
    'driver'   => 'smtp',
    'host'     => 'smtp.example.com',
    'port'     => 587,            // 只支持 STARTTLS；465 未实现
    'user'     => 'noreply@example.com',
    'password' => 'xxxxxxxx',
    'from'     => 'noreply@example.com',
],
```

**② 后台 → 配置 → 合规与隐私**：

- 「确认码发送渠道」—— 自动（有手机号发短信，否则邮件）/ 只短信 / 只邮件
- 「隐私政策网址」—— 会附在消息里。留空则不附，但**现场仍须口头告知**

**③ 后台 → 配置 → 合规与隐私 → 「允许收集客人联系方式」** 打开。

打开时会弹窗确认；如果渠道还没配好，**后台顶部会一直挂一条红条**，
直到配好或把开关关掉 —— 这个提醒不会自己消失，就是为了别拖着忘掉。

### 11.2 开启后收银台的流程

```
扫卡 → 展开「选填：留联系方式」→ 填手机号 → 启用这张卡
     → 系统发码 → 客人报码 → Pad 输入 → 积分解冻
```

客人不想等可以点「稍后再说」—— 卡照常能用、积分照常入账，
只是暂时不能兑换，下次到店再补确认即可。

### 11.3 验证发送通不通

配好之后先拿自己的手机试一次：开启开关 → 扫一张测试卡 → 填自己的号码 →
看能不能收到码。收不到就去看服务器错误日志，里面有服务商返回的原始错误
（Twilio 的错误码很具体，比如 `21211` 是号码格式不对、
`21608` 是试用账号没验证过这个号码）。
