# 00 · 架构总览

## 1. 设计约束

POS 系统视为**完全黑盒且不可修改**。放弃一切基于 POS 主动推送或配置修改的方案（包括主库中存在的 `vip_setting` 外部会员服务器接口——启用它需要改 POS 配置，不符合约束）。

系统采用**无侵入式旁路监听架构**：侧系统只以只读方式观察 POS 主库，自身完整持有会员、积分、卡券的全部状态。

| 约束 | 含义 |
|---|---|
| POS 主库只读 | 仅 `SELECT`。不写入、不建表、不改配置、不装触发器 |
| POS 主机性能受限 | 查询必须命中索引、限制步长、限定字段。见 `02-只读接入规范.md` |
| 网络单向 | 门店可访问外网（出站），外网不可访问门店（无入站） |
| 内网域名访问 | Pad 通过内网域名访问侧系统 |

## 4. 内网域名与证书

### 4.1 域名后缀选择

**不建议使用 `.local`**：该后缀由 RFC 6762 保留给 mDNS，部分 iOS/Android 会走 Bonjour 解析而不查路由器 DNS，导致间歇性解析失败。

**推荐方案**：注册一个真实域名的子域（如 `vip.<餐厅域名>.com`），DNS A 记录指向侧系统的**内网 IP**。

| 方案 | 解析 | HTTPS 证书 | 流量路径 |
|---|---|---|---|
| `vip.local.pos` + 路由器 DNS | ⚠️ `.local` 有 mDNS 冲突风险 | ❌ 签不出公信证书 | 局域网 |
| **真实子域 + 公网 DNS 指内网 IP** | ✅ 稳定 | ✅ Let's Encrypt **DNS-01** 签发 | ✅ 全程局域网 |

第二种方案下：证书由 DNS-01 challenge 签发（不需要 80/443 入站），域名解析在公网完成，实际流量全部走局域网。完全契合"仅出不进"的网络策略。

### 4.2 为什么必须上 HTTPS

Pad 浏览器在非安全上下文（HTTP）下会限制部分 Web API，密码输入框会显示告警，且会员手机号等 PII 在局域网内明文传输。**HTTPS 是硬要求，不是可选项。**

## 5. 数据流总览

### 5.1 积分发放（收银员触发，同步）

```
收银员在 Pad 输入：桌号 + 会员标识(卡号/手机号/邮箱)
        │
        ▼
/app 向 POS 主库发起【单点查询】
  history_order_head
  WHERE order_end_time >= NOW() - INTERVAL 30 MINUTE   ← 走 idx_order_end_time
    AND table_name = ? AND eat_type = 0
        │
        ▼
/app 侧按 order_head_id 聚合 → Pad 显示候选订单（通常 1 条）
        │
        ▼
收银员确认订单 → /app 读取该订单明细（主键单点查）
                 · 计次份数（counts_visit=1 的 SUM(quantity)）
                   ↳ 实际计几次由 visit_count_mode 决定，
                     现行口径是「一张卡一个餐期最多 1 次」（03 §13）
                 · 不计分项金额扣除
        │
        ▼
收银员选择记账方式（整单 / 均摊 AA / 点选菜品）
        │
        ▼
写入本地库：pos_order + point_ledger（追加式账本）
```

### 5.2 数据校准（定时任务，异步）

```
Cron（错峰执行，建议 03:00-05:00）
        │
        ├─► 增量补抓：从上次水位线起，按 48 小时窗口滚动
        │            history_order_head，LIMIT 100 分页
        │
        └─► 值比对冲正：回读本地已发分订单的 serial_id
                     金额不一致 → 写冲正流水
```

详见 `03-积分与防刷引擎.md`。

## 6. 关键技术决策与依据

| 决策 | 依据 | 详见 |
|---|---|---|
| 用 `serial_id` 作业务主键，不用 `order_head_id` | `serial_id` 是 POS 生成的业务流水号（`YYMMDD`+4 位），非自增代理键，数据库迁移/重建不受影响 | 01 §2.1 |
| 只读 `history_order_head`，不读 `order_head` | `order_head` 上**没有任何时间索引**，按时间查必然全表扫 | 01 §6 |
| 积分基数 = `LEAST(should_amount, actual_amount)` | `actual_amount` 是**收款额含待找零**，直接用会把找零算成消费；`LEAST` 兼顾"有找零时取应收"与"10送1 时为 0 不积分" | 01 §2.2、03 §2 |
| 退单巡检用**值比对**而非 `return_time` 扫描 | 实测退菜 100% 发生在结账前，金额已在 `should_amount` 中扣除，按 `return_time` 扫会重复扣分 | 03 §6 |
| Pad 端按 `order_head_id` 聚合后再展示候选 | 按 check 行返回歧义率 10.95%，聚合后降至 **0.02%** | 03 §1 |
| Apple Wallet 使用静态 pass | 仅作身份识别，不显示余额，无需 Apple 服务器回连门店 | 05 §3 |
