# 02 · 只读接入规范

> POS 主机配置较低，**绝不允许因侧系统轮询导致主业务卡顿或死机**。本文档的规则是硬性约束，不是建议。

## 1. 五条铁律

### 铁律 1 —— 禁止全表扫描，强制命中索引

| 场景 | 表 | 必须命中的索引 | 条件字段 |
|---|---|---|---|
| 新单定位 | `history_order_head` | `idx_order_end_time` | `order_end_time` 范围 |
| 增量补抓 | `history_order_head` | `idx_order_end_time` | `order_end_time` 范围 |
| 单订单回读 | `history_order_head` | `idx_headcheck` | `order_head_id` + `check_id` |
| 明细读取 | `history_order_detail` | `idx_detailcheck` | `order_head_id` + `check_id` |

**禁止事项：**

- ❌ 按时间范围查询 `order_head`（**该表没有时间索引**，必然全表扫）
- ❌ 全表扫描 `history_order_detail`（约 138 万行）
- ❌ 任何不带 `WHERE` 索引条件的查询
- ❌ 对 `table_name`、`serial_id` 等无索引字段做范围/模糊查询

### 铁律 2 —— 步长控制与分页

- 每次查询**必须**追加 `LIMIT`，上限 **100**
- 断网恢复后的积压数据，必须分批消化，**批次之间强制停顿**（建议 2 秒）
- 单次任务的总批次数设上限（如 200 批），超出则记录告警并留到下次

### 铁律 3 —— 字段级精准抽取

**禁止 `SELECT *`。** 各场景的字段白名单：

```sql
-- 场景 A：订单定位 / 增量补抓
SELECT serial_id, order_head_id, check_id, table_name, eat_type,
       customer_num, should_amount, actual_amount, order_end_time

-- 场景 B：金额回读（值比对冲正）
SELECT serial_id, should_amount, actual_amount, edit_time

-- 场景 C：明细读取（AA 点选菜品 / 免费餐兜底）
SELECT menu_item_id, menu_item_name, quantity,
       product_price, original_price, actual_price,   -- 三个价格字段都要，用于区分两种 0 元
       is_discount + 0 AS is_discount,
       is_return_item + 0 AS is_return_item,
       condiment_belong_item
```

> **为什么三个价格字段都要取**：`actual_price = 0` 有两种截然不同的含义 —— 「套餐内本来就免费的菜」（三个字段全 0/NULL，UI 隐藏）与「被免掉的收费项」（`product_price` 或 `original_price` 保留原价，UI 必须显示）。详见 `03-积分与防刷引擎.md` §3.C.1。

> **注意**：`actual_amount` 与 `should_amount` **两个都要取**，因为积分基数是 `LEAST()` 的结果，需要在 `/app` 侧计算（不在 SQL 里算，保持 SQL 朴素）。

### 铁律 4 —— 错峰与拉长周期

| 任务 | 触发方式 | 频率 | 时段 |
|---|---|---|---|
| 新单定位 | 收银员在 Pad 操作时**按需触发** | 事件驱动，无轮询 | 营业时间 |
| 明细读取 | **每次积分操作必读**（计次需要，见 `03` §3.2） | 事件驱动，每次积分 1 次 | 营业时间 |
| 增量补抓 | Cron | 每 15–30 分钟 | 营业时间 |
| 滚动校准 | Cron | 每 48 小时窗口 | **03:00 – 05:00** |

> 每次积分操作 = **2 次查询**：订单头时间范围查（走 `idx_order_end_time`）+ 明细主键单点查（走 `idx_detailcheck`）。按日均 95.6 单估算，全天不到 200 次查询，对 POS 无压力。

**03:00–05:00 的依据**：实测 02:00–10:00 全时段 0 单结账，是唯一绝对安全的窗口。注意营业延续到凌晨 01:00（00 点 1,036 单、01 点 27 单），**不要把"下班后"理解成 00:00**。

### 铁律 5 —— 超时兜底（MySQL 5.5 无服务端超时）

`MAX_EXECUTION_TIME` 是 MySQL **5.7.4** 引入的，**5.5 上不存在**，服务端无法自动掐断慢查询。必须在客户端兜底：

```php
$mysqli = mysqli_init();
$mysqli->options(MYSQLI_OPT_CONNECT_TIMEOUT, 3);
$mysqli->options(MYSQLI_OPT_READ_TIMEOUT, 5);   // ← 关键：PDO::ATTR_TIMEOUT 只管连接不管查询
$mysqli->real_connect($host, $user, $pass, $db, $port);
```

- 连接超时 3 秒，读超时 5 秒
- 超时后**不重试**，记录告警，留到下个周期
- 连接使用后立即关闭，不做长连接池（避免占用 POS 的连接数）

POS 系统中**已存在只读账号**，直接使用。

**配置文件示例**（`/app/config/pos_db.php`，不入版本库）：

```php

    'host'     => '192.168.2.40',
    'port'     => 3308,
    'database' => 'coolroid',
    'user'     => '<只读账号>',
    'password' => '<密码>',
```

## 3. SQL 模板

### 3.1 订单定位（收银员触发）

```sql
SELECT serial_id, order_head_id, check_id, table_name, eat_type,
       customer_num, should_amount, actual_amount, order_end_time
FROM history_order_head
WHERE order_end_time >= NOW() - INTERVAL ? MINUTE   -- 后台可配，默认 30
  AND table_name = ?
  AND eat_type = 0                                   -- 白名单：仅堂食
ORDER BY order_end_time DESC
LIMIT 20;
```

- 走 `idx_order_end_time`
- **时间基准用主库 `NOW()`**，不用 PHP 时间（避免时钟/夏令时偏差）
- **不写 `GROUP BY`** —— 取回最多 20 行，在 `/app` 侧按 `order_head_id` 聚合
- 峰值时段 30 分钟内全店最多 54 单，单桌过滤后通常 1–2 行

### 3.2 增量补抓（Cron）

```sql
SELECT serial_id, order_head_id, check_id, table_name, eat_type,
       customer_num, should_amount, actual_amount, order_end_time
FROM history_order_head
WHERE order_end_time >= ?          -- 上次水位线
  AND order_end_time <  ?          -- 水位线 + 48 小时
ORDER BY order_end_time ASC
LIMIT 100;                         -- 分页，OFFSET 递增
```

**水位线处理：**

- 用 `>=` 而非 `>`，靠 `serial_id` 在本地做幂等去重（避免同秒边界丢单）
- 水位线只在**整批成功落库后**才前移
- 水位线值取自**主库返回的 `order_end_time`**，不用本地时间

### 3.3 金额回读（值比对冲正）

```sql
SELECT serial_id, should_amount, actual_amount, edit_time
FROM history_order_head
WHERE order_head_id = ? AND check_id = ?;
```

走 `idx_headcheck`，主键单点查，开销极小。批量回读时逐条执行并在批次间停顿，**不要拼 `IN (...)` 大列表**。

### 3.4 明细读取（AA 点选菜品 / 免费餐兜底）

```sql
SELECT menu_item_id, menu_item_name, quantity,
       product_price, original_price, actual_price,
       is_discount + 0 AS is_discount,
       is_return_item + 0 AS is_return_item,
       condiment_belong_item
FROM history_order_detail
WHERE order_head_id = ? AND check_id = ?
  AND menu_item_id > 0
  AND condiment_belong_item = 0
LIMIT 100;
```

- 走 `idx_detailcheck`
- `is_return_item + 0` / `is_discount + 0` —— **必须**做类型转换，否则 PHP 读到的是二进制字节
- 退菜行与套餐内 0 元菜品**均在 `/app` 侧过滤**（不放进 SQL，让索引条件保持最简）
- 单订单明细通常 5–30 行，`LIMIT 100` 足够

## 4. 全量与增量策略

### 4.1 上线一次性全量

系统上线时做一次全量导入，建立初始基线：

- 只扫 `history_order_head`（88,616 行）
- **绝不全量扫 `history_order_detail`（138 万行）**
- 按 `order_end_time` 升序，`LIMIT 100` 分页，批次间停顿 2 秒
- 88,616 行 ≈ 887 批 ≈ 30 分钟，**必须在 03:00–05:00 窗口内分夜执行**

### 4.2 日常增量

从上次水位线起，按 **48 小时窗口滚动**。

**为什么是 48 小时**：系统无法保证 24 小时开机，收银员也可能忘记触发校准。48 小时窗口意味着漏掉一天也能自动补齐。

**积压追赶**：一次任务内循环执行多个 48 小时批次，直到水位线追上当前时间，批次之间停顿。

| 积压时长 | 订单数（日均 95.6） | `LIMIT 100` 分页数 | 48h 批次数 |
|---|---|---|---|
| 48 小时 | ~190 | 2 | 1 |
| 一周（168h） | ~665 | 7 | **4**（168 ÷ 48 = 3.5，向上取整） |
| 一个月 | ~2,870 | 29 | 15 |

> ⚠️ 一周积压需要 **4 个** 48 小时批次（不是 3 个）。按"循环到追上"实现即可，不需要人工判断次数。

即使一周积压，总计 7 页 × (查询 + 2 秒停顿) ≈ 20 秒跑完，POS 无感知。

## 5. 监控与告警

`/app` 侧需记录每次 POS 查询的：

| 指标 | 告警阈值 |
|---|---|
| 查询耗时 | 单次 > 2 秒 |
| 连续超时次数 | ≥ 3 次 |
| 水位线滞后 | > 72 小时（说明 Cron 长期未成功执行） |
| 单批返回行数 | 持续等于 `LIMIT` 上限（说明积压未消化完） |

**降级策略**：主库连续不可达时，Pad 端积分请求进入本地队列，提示收银员"稍后自动补记"，恢复后由校准任务补齐。**绝不因主库不可达而阻塞收银流程。**
