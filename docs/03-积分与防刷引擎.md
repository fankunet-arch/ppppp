# 03 · 积分与防刷引擎

## 0. 两条找单路径

收银员有两种方式定位订单，Pad 上并存，默认落在「小票号」：

| 方式 | 键 | 适用 | 限制 |
|---|---|---|---|
| **小票号**（推荐） | `order_head_id`（小票上的 `Factura Simplificada`） | 客人手里有小票 | 仅受回溯天数上限约束（`invoice_lookup_max_days`，默认 7 天） |
| 桌号 | `table_name` + 时间窗 | 客人没拿小票 | 30 分钟窗口；翻台时可能出多个候选 |

**为什么优先用小票号**（依据见 `01` §2.9）：

- `Factura Simplificada` = `order_head_id`，**全局唯一**，两张实物小票已验证
- 不受 30 分钟窗口限制 —— 客人隔天拿小票来也能补记
- 不受翻台影响，分单的多张 check 一次全取回
- 查询代价更低：`WHERE order_head_id = ?` 命中 `idx_headcheck`，
  `type=ref, rows=1` 单点查，比按时间范围扫还便宜

> 🔴 **不要用小票上的「Número Ticket」当键。** 那是 `check_number`，
> 实测当日会重号（2026-08-03 票号 323 在 13:05 与 21:36 各发过一次），
> 63 天里有 11 天重复。它只能用来跟收银员口头核对，不能做查询键。

**外带单按小票号查得到**（不过滤 `eat_type`）—— 目的是让收银员看到
「外带订单不积分」的明确提示，而不是「查无此单」让人以为号输错了。

## 1. 订单定位

### 1.1 交互流程

```
收银员在 Pad 输入：
  ① 桌号（堂食）
  ② 会员标识 —— 三选一：卡号 / 完整手机号 / 邮箱（UI 上明确选择输入类型）
        │
        ▼
/app 查询 history_order_head（近 30 分钟 + 该桌号 + eat_type=0）
        │
        ▼
/app 侧按 order_head_id 聚合（同一订单的多张 check 合并求和）
        │
        ▼
Pad 展示候选订单：桌号 / 金额 / 人数 / 结账时间
        │
        ▼
收银员确认订单
        │
        ▼
★ /app 读取该订单明细（history_order_detail，主键单点查）
   · 累加 counts_visit=1 菜品的 quantity  → 计次份数（§3.2）
   · 累加 earns_points=0 菜品的金额        → 积分基数扣除（§2.3）
   · 供「点选菜品」模式展示                （§3 模式 C）
        │
        ▼
收银员选择记账方式（整单 / 均摊 AA / 点选菜品）→ 提交
```

> ⚠️ **流程变更**：计次已下沉到菜品级（`MENÚ DEL DIA` 不计次、儿童套餐可配），因此**每次积分都必须读一次订单明细**，不再只有「点选菜品」模式才读。
>
> 性能影响可忽略：单订单明细 5–30 行，走 `idx_detailcheck` 主键单点查。每次积分操作共 **2 次查询**（1 次订单头时间范围查 + 1 次明细主键单点查）。

### 1.2 为什么必须按 `order_head_id` 聚合

实测 76,523 笔可积分订单（堂食 + `actual_amount > 0`），模拟"结账后 1/5/10/15/20/25/30 分钟查询"共 53 万次：

| 返回方式 | 窗口 15 分 | 窗口 30 分 | 窗口 45 分 | 窗口 60 分 |
|---|---|---|---|---|
| 按 check 行直接返回 | 10.36% | **10.95%** | 11.61% | 11.81% |
| **按 `order_head_id` 聚合后返回** | 0.01% | **0.02%** | 0.06% | 0.23% |

**歧义主因拆解（30 分钟窗口）**：同一订单分单造成 **8,873** 次，真正翻台造成的仅 **14** 次。

> 结论：歧义几乎全部来自"同一桌同一单的多张 check"，聚合后即消失。53 万次模拟中仅 127 次返回 2 条订单，此时 Pad 展示金额让收银员点选即可。

### 1.3 窗口时长

- 后台可配置，**默认 30 分钟**
- 窗口拉长收益极小（15→60 分钟，聚合后歧义仅从 0.01% 升到 0.23%），但会增加误选风险
- 时间基准**必须**用主库 `NOW()`

### 1.4 外带订单

**外带（`eat_type = 3`，占 11.84%）不积分。**

原因：全部 10,495 单的 `table_name` 恒为 `'Llevar'` / `'Paquetear'`，桌号定位歧义率高达 81.40%，无法可靠识别。

实现上用**白名单** `eat_type = 0`，不要写 `eat_type != 3`（库中还有 `eat_type = 1`(3单)、`= 2`(4单) 来路不明的记录，白名单可自动排除）。

## 2. 积分基数

```
积分基数 = LEAST(should_amount, actual_amount)
```

在 `/app` 侧计算，不在 SQL 内计算。

| 场景 | should | actual | 基数 | 说明 |
|---|---|---|---|---|
| 正常消费（付清） | 58.30 | 58.30 | 58.30 | 两者相等 |
| **现金找零** | 105.35 | 115.35 | **105.35** | 客人递 115.35，找零 10.00，实际消费 105.35 |
| **递整钞** | 127.85 | 135.00 | **127.85** | 客人递整钞 135，找零 7.15 |
| 分币舍入 | 41.70 | 41.80 | **41.70** | 抹到 5 分位 |
| 10送1 免费餐 | 0.00 | 0.00 | **0.00** | 不积分 |
| 员工餐/招待 | 0.00 | 0.00 | **0.00** | 不积分 |

> 🔴 **`actual_amount` 是「收了客人多少钱」，包含待找零部分，不是净实付额。**
>
> 实测 172 行（0.19%）`actual_amount > should_amount`，差额呈 `+5.00` / `+10.00` / `+15.00` 及整钞 40/130/135 的模式；88 个大额差中 57 个 `actual_amount` 为整数；`actual_amount < should_amount` 全表仅 1 行。详见 `01-POS主库数据字典.md` §2.2。
>
> **直接用 `actual_amount` 积分会把找零算成消费额**。最大一笔 `should=27.40 → actual=54.80`（正好 2 倍，疑似重复收款录入），会多给一倍积分。
>
> `LEAST()` 一个表达式覆盖全部场景：有找零时取 `should_amount`（真实消费额），免费餐时两者皆为 0。

### 2.1 含税说明

金额为**含 IVA 10%** 的口径（实测 `SUM(tax_amount)/SUM(should_amount) = 9.09% = 10/110`，菜单标价即含税价）。

**积分按含税价计算** —— 已确认。

### 2.2 硬性过滤条件

```
可积分 = (eat_type == 0)
       AND (LEAST(should_amount, actual_amount) > 0)
       AND (未被标记为免费餐)
```

`actual_amount = 0` 的订单共 1,666 单（1.88%，按月均匀分布 40~78 单），**既不积分也不计次**。

### 2.3 不计积分项的金额扣除

当某菜品在 `meal_item_rule` 中 `earns_points = 0` 时（如后台关闭了 `MENÚ DEL DIA` 的积分），需从积分基数中**按比例**扣除：

```
排除金额 = SUM(history_order_detail.actual_price)  WHERE meal_item_rule.earns_points = 0
                                                    （actual_price 已是行小计，勿乘 quantity）

积分基数 = LEAST(history_order_head.should_amount, history_order_head.actual_amount)
           × (1 - 排除金额 / history_order_head.original_amount)
```

> ✅ **分母用 `original_amount`**：实测 153/153 = 100% 满足 `SUM(actual_price) == original_amount`（见 `01` §3.3.1），直接取订单头字段即可，无需在 `/app` 侧再累加明细，且明细偶发不全时不会失真。

> ⚠️ **必须按比例扣，不能直接相减。** 明细行金额是**折扣前**口径，而积分基数是折扣后的实际消费额 —— 订单级折扣只记在 `history_order_head.discount_amount`，不体现在明细行上（实测 4.79% 的订单有折扣）。按比例扣可自动吸收这个差异。
>
> 实例：`original_amount = 114.10`、`discount_amount = -14.34`、`should_amount = 99.76`，而明细 `SUM(actual_price) = 114.10`。

> 🔴 **`actual_price` 已经是行小计，绝不可再乘 `quantity`。**
>
> 实测 242 行 `quantity > 1` 的明细，**100% 满足 `actual_price = product_price × quantity`**（如 3 份 MENÚ INFINITY：`product_price = 23.90`、`actual_price = 71.70`、`quantity = 3`）。再乘一次会让金额平方级放大（71.70 × 3 = 215.10）。详见 `01-POS主库数据字典.md` §3.3。

## 3. 记账方式（服务员选择）

同一订单可被**多个会员**分别积分，三种模式由服务员在 Pad 上选择：

### 模式 A —— 整单记给一人

```
会员 X 获得：金额 = 订单全额
             次数 = 订单内 counts_visit=1 菜品的 SUM(quantity)（见 §3.2）
```

### 模式 B —— 均摊 AA

```
Pad 上输入人数 N（默认取 history_order_head.customer_num）
每人金额 = 订单全额 / N
每人次数 = 计次份数总和 / N（余数给第一位）
```

- 除不尽时，**余数分配给第一位会员**（保证 `SUM(分摊) == 订单全额`，分毫不差）
- 允许只登记其中部分人（如 4 人 AA 但只有 3 人有卡），剩余份额保持未分配状态

### 模式 C —— 点选菜品

读取 `history_order_detail`，让每位会员认领自己点的菜。

**⚠️ 套餐店特殊性**：这家店 86.9% 的菜品单价为 `0.00`（套餐内无限点）。真正有金额的只有**套餐主项**（`MENÚ INFINITY = 23.90` 等）和**饮料酒水甜点**。

#### 3.C.1 显示规则

Pad 上**只显示有金额的项**，套餐内的 0 元菜品不显示（列表太长、且不影响分摊）。

**但有一个必须处理的特例**：当套餐本身被免费时（10送1 那一次），`MENÚ INFINITY` 的实收金额也是 `0.00`。若按"只显示有金额的项"直接过滤，享用免费餐的那位客人在列表里**什么都认领不到**。

**判据**（不依赖分组白名单）：明细表的三个价格字段能区分两种 0 元 ——

| `product_price` | `original_price` | `actual_price` | 含义 | 显示 |
|---|---|---|---|---|
| `0` | `NULL` | `0` | **套餐内菜品**（本来就免费） | ❌ 隐藏 |
| `>0` | `NULL` | `>0` | 正常收费项 | ✅ 显示 |
| `>0` | `NULL` | **`0`** | **被免的收费项**（伴随 `is_discount = 1`） | ✅ **显示** |
| `0` | **`>0`** | `0` | **被免的收费项**（另一种记法） | ✅ **显示** |

```
显示 = (actual_price > 0) OR (product_price > 0) OR (original_price > 0)
隐藏 = 三者全为 0 / NULL
```

被免的收费项**总会在 `product_price` 或 `original_price` 上保留原价痕迹**（实测：`Agua` 原价 2.80 实收 0、`Verdejo` 原价 13.95 实收 0），而套餐内菜品三个字段全为 0/NULL。

> 📊 **样本说明**：该判据基于 100 行明细样本（4 种组合分别为 68 / 6 / 4 / 2 行）。组合分布清晰但样本量小，**建议上线前用更大样本（如近 30 天明细）复验一次**，确认没有第五种组合。

#### 3.C.2 UI 要求

- 被免的项（实收 0 但有原价）→ 显示时标注 `原价 23.90 → 已免`，让客人看得懂
- 有价项视觉突出（加粗/标金额）
- 实际效果：每人认领自己那份 MENÚ 套餐 + 自己的酒水，天然形成 AA；享用免费餐的那位也能正常认领

**明细过滤**（见 `02-只读接入规范.md` §3.4）：

```
menu_item_id > 0            排除 -3 备注行、-4 支付方式行
condiment_belong_item = 0   排除配料/做法行
is_return_item + 0 = 0      排除已退菜行
三个价格字段全为 0/NULL      排除套餐内菜品（仅影响显示，不影响金额计算）
```

### 3.1 金额守恒约束

无论哪种模式，恒定成立：

```
SUM(point_ledger.amount WHERE serial_id = X 且未撤销)  ≤  pos_order.total_amount
```

每次积分前校验 `allocated_amount + 本次金额 ≤ total_amount`，超出即拒绝并提示"该订单已全额积分"。

### 3.2 计次规则 —— 按「套餐份数」计次（已确认）

`MENÚ DEL DIA` 不参与十送一这条规则，使**计次从订单级下沉到菜品级**。由此得到统一的计次口径：

```
计次 = 该会员认领的、meal_item_rule.counts_visit = 1 的菜品的
       SUM(history_order_detail.quantity)
```

> ⚠️ **份数用 `SUM(quantity)`，不是 `COUNT(*)`。** 收银员会把多份相同套餐录成一行（实测 `quantity` 有 2、3、4、5 的行，如一行 5 份 MENÚ INFINITY）。按行数统计会严重少算。
>
> 📌 注意与金额的区别：**金额直接用 `actual_price`（已是行小计），份数才用 `SUM(quantity)`。** 两者不要混。

这个口径同时自洽地解决了 AA 场景：

| 场景 | 明细构成 | 计次结果 |
|---|---|---|
| 整单记给一人 | 3 份 MENÚ INFINITY | 该会员 **+3 次** ✅ 已确认接受 |
| AA 3 人均摊 | 3 份 MENÚ INFINITY | 每人 **+1 次** |
| 混点 + AA 3 人 | 2 份 INFINITY + 1 份 DEL DIA | 吃 INFINITY 的两人各 +1，吃 DEL DIA 的 **+0** |
| 儿童同行（后台关闭儿童计次） | 2 份成人 + 1 份儿童 | 成人各 +1，儿童套餐 **+0** |
| 只点单品无套餐 | 0 份计次套餐 | **+0 次**（但金额照常积分） |

**商业含义**：十送一 = 「吃 10 份套餐送 1 份」，按份数计次最贴合活动本意。

> 📌 已确认采用 `visit_count_mode = by_portion`。整单记一人时 3 份 = +3 次，3 人同行来 4 次即可换 1 份免费餐 —— 此商业影响已知悉并接受。
> 备用口径 `by_ledger`（每笔流水最多 1 次）保留在配置中，如需切换可随时改，`portions_counted` 快照字段支持历史数据重算。

**均摊 AA 时的份数分配**：按人数均分计次份数；除不尽时余数分配给第一位会员（与金额分摊规则一致）。

**点选菜品时**：份数按各人实际认领菜品的 `quantity` 累加，天然精确。

## 4. 撤销

### 4.1 设计原则：追加式账本（Append-only）

**撤销 = 写一条反向冲正流水，绝不物理删除原流水。**

理由：
- 西班牙会计/税务留存义务
- 全流程可审计
- 避免并发删除导致的金额守恒破坏

```
原流水:  id=101  member=A  amount=+58.30  points=+58  status=active
撤销后:  id=101  member=A  amount=+58.30  points=+58  status=reversed  reversed_by=102
         id=102  member=A  amount=-58.30  points=-58  type=reversal    reverses=101
```

同时 `pos_order.allocated_amount` 回退，订单状态从 `fully_allocated` 回到 `open`，可重新分配。

### 4.2 典型场景

> 服务员先把整单记给了一个人，客人说要分别记给每一个人，且其中一位客人还没有卡。

流程：

```
1. 服务员在 Pad 调出该订单（按桌号或会员近期流水）
2. 点击"撤销记账" → 系统写冲正流水，订单回到 open 状态
3. 服务员改选"均摊 AA"，输入人数
4. 对没有卡的客人 → 内联"新增会员"（见 §4.4）
5. 逐个登记，直到分配完毕
```

### 4.3 撤销的约束

| 项 | 建议值 | 状态 |
|---|---|---|
| 时间窗 | 当班内（营业日内）可自由撤销 | 🟡 待确认 |
| 超时窗后 | 需经理权限 | 🟡 待确认 |
| 权限 | 服务员可撤销自己当班登记的；跨班/跨日需经理 | 🟡 待确认 |
| 已消费积分 | 若积分已被兑换，撤销会导致负余额 → **允许负余额并标记**，不阻断撤销 | 建议 |
| 审计 | 每次撤销记录操作人、时间、原因 | 必须 |

### 4.4 内联新增会员（配合 LOPDGDD）

积分流程中可直接创建会员，但必须走合规路径：

```
新建会员 → 状态 pre_registered
        → 积分正常入账，标记 consent_status = pending
        → 系统立即发送 double opt-in 短信/邮件（含隐私政策链接）
        → 客人点击同意 → 状态 active，积分解冻可用
        → N 天（默认 30）未同意 → 积分冻结 + PII 假名化
```

**关键**：积分**当场就要入账**（客人马上要走），但在同意前**不可用于兑换、不可用于营销推送**。详见 `05-合规与Wallet.md`。

## 5. 免费餐（10送1）识别

### 5.1 主路径：Pad 端核销标记

10送1 的核销**本来就发生在侧系统**，我们自己知道：

```
收银员在 Pad 点击"使用免餐券"
     → 本地标记该 serial_id 为 is_free_meal = 1
     → 该单不计次
     → 额外消费（饮料甜品）是否计入金额积分：后台开关控制
     → 收银员再到 POS 端手动做对应折扣收银
```

**不依赖 POS 判断。**

### 5.2 兜底：防止收银员漏点

风险：收银员忘了在 Pad 点核销，直接在 POS 打折 → 我们当成正常消费计次了。

**兜底校验**（校准任务中执行），分两层：

**第一层 —— 「被免金额」信号（不需要白名单，可立即上线）**

利用 §3.C.1 的价格字段判据，订单级计算：

```
被免金额 = SUM( COALESCE(NULLIF(original_price,0), product_price) - actual_price )
           WHERE 该差值 > 0

若  被免金额 > 0
且  本地未标记 is_free_meal
则  → 后台报警，人工复核
```

> ⚠️ 这一层会同时捕捉到**普通赠送**（送一瓶水 2.80）和**免餐券**（免掉 23.90 的套餐），需要按金额量级设阈值，或用第二层精确区分。

**第二层 —— 「餐费项被免」精确判据（需要规则表）**

```
若  订单内【存在】is_meal_fee = 1 的明细行     ← 关键前置条件
且  这些行的金额合计 == 0
且  订单 LEAST(should, actual) > 0            ← 说明只剩饮料甜品的钱
且  本地未标记 is_free_meal
则  → 后台报警，人工复核
```

> 🔴 **前置条件「存在餐费项」不可省略。** 若写成"餐费项合计 == 0"，则**根本没点套餐的订单会被全部误报** —— 例如堂食客人点了一份 `COMBO L`（45.00，属 `major_group = 1 Comida`，不是餐费项）配酒水，餐费项合计天然为 0 且订单有金额，正好命中条件。
>
> 免费餐的真实特征是「**点了套餐但套餐被免**」，不是「没点套餐」。

> ⚠️ **绝不能用"单行 `actual_price = 0`"判断**。这家店 86.9% 的菜品单价本来就是 0（套餐内无限点），按单行判断会把每一单都误判成免费餐。必须用**订单级的餐费项合计**。

### 5.3 「餐费项」白名单（已确定）

分组名称已确认：`major_group` = `1 Comida` / `2 Bebida` / **`3 Menú`** / `4 Postres`。套餐（`major_group = 3`）占全期销售额 **78.55%**，是餐费主体。

但 `major_group = 3` 共 19 项，**不能整组当餐费** —— 组内混有餐具、调料、外送费。精确白名单为其中 **7 项**：

规则**不硬编码**，存于后台可维护的 `meal_item_rule` 表（见 `04-本地库Schema.md` §6.2）。每个套餐项有三个**互相独立**的开关：

| menu_item_id | 名称 | 参考价 | `is_meal_fee` | `counts_visit` | `earns_points` |
|---|---|---|---|---|---|
| `2590` | MENÚ INFINITY VIERNES NOCHE-FIN DE SEMANA | 25.90 | 1 | 1 | 1 |
| `25900` | TAKE WAY | 25.90 | 1 | 1 | 1 |
| `2390` | MENÚ INFINITY NOCHE LUNES A JUEVES | 23.90 | 1 | 1 | 1 |
| `1890` | MENÚ INFINITY MEDIODIA - ADULTOS | 18.90 | 1 | 1 | 1 |
| `1590` | **MENÚ DEL DIA** | 15.90 | 1 | **0** | 1 |
| `1490` | MENU INFANTIL NOCHE | 14.90 | 1 | **1** ⚙️ | 1 |
| `1290` | MENÚ INFINITY - INFANTIL MEDIODIA | 12.90 | 1 | **1** ⚙️ | 1 |

- **`1590` MENÚ DEL DIA**：`counts_visit = 0` —— 不参与十送一。金额积分默认计入，可关。
- **`1490` / `1290` 儿童套餐**：⚙️ **后台可自由切换**是否参与十送一，默认参与。

| 开关 | 作用 |
|---|---|
| `is_meal_fee` | 免费餐兜底判据（§5.2 第二层）用 |
| `counts_visit` | 计次：`SUM(quantity)` where `counts_visit = 1`（§3.2） |
| `earns_points` | 为 `0` 时，该项金额按比例从积分基数中扣除（§2.3） |

**未被规则表覆盖的菜品，按安全默认值处理：**

```
is_meal_fee = 0    不参与免费餐判据
counts_visit = 0   不计次
earns_points = 1   金额正常积分
```

> 这组默认值保证「漏配一个项」的后果**只是少计次，不会算错钱、不会误报免费餐**。

**✅ 外卖产品线 `BOX` / `COMBO`（22 项）—— 三个开关全 `0`**

> **业务规则：BOX 属外卖产品，堂食客人不可点。若堂食单中出现 BOX，仍按外卖处理，一律不计入。**
>
> `is_meal_fee = 0`、`counts_visit = 0`、**`earns_points = 0`** —— 最后一项会让该行金额通过 §2.3 的按比例扣除机制从积分基数中剔除。堂食单若全部是 BOX，排除金额 = 全额，积分基数归零，自动不积分。
>
> 实测佐证：跨 2024-01 与 2026-08、220 个订单，**20 行 BOX/COMBO 全部出现在 `eat_type = 3` 订单，堂食 0 行**。`COMBO S/M/L/XL` 按同产品线处理。
>
> 完整 22 项清单与 INSERT 语句见 `04-本地库Schema.md` §6.2.1。

**同组但明确排除的 12 项**：`6046` PORTES（外送费）、`1200`/`1100` Suplemento、`43435` Palillos、`555` Tenedor、`666`/`777` Wasabi、`43445` Jengibre、`43447` Vaso y Hielo、`43457` Cuchara、`43458` Cuchillo、`888` Temporal。

完整对照表见 `01-POS主库数据字典.md` §4.2。

### 5.4 白名单的维护机制（必须建立）

菜单会变。实测：2024-01 时 `item_id=2390` 名为 `MENÚ INFINITY NOCHE-FESTIVO-FIN DE SEMANA-ADULTOS`（23.90），现改为 `NOCHE LUNES A JUEVES-ADULTOS`；周末套餐被拆成新项 `2590` 并涨价至 25.90。

**因此需要：**

1. **后台维护界面** —— 白名单可视化编辑，不写死在代码里
2. **自动巡检**（随日常校准执行）：

```
扫描 menu_item 中 price_1 >= meal_item_alert_price（默认 8.00）
     且 item_id 不在 meal_item_rule 表中的项
  →  后台提醒「菜单出现未归类的高价项，请确认三个开关」
```

> 🔴 **不能只扫 `major_group = 3`。** 实测 BOX / COMBO 系列共 **22 项**（`BOX 1`~`BOX 18`、`COMBO S/M/L/XL`，价格 10.00~65.00）位于 **`major_group = 1 (Comida)` / `family_group = 7 (Sushis)`**，只扫 `major_group = 3` 会全部漏掉。
>
> 巡检必须按**价格阈值**扫全表，不能按分组过滤。
>
> 阈值取 **8.00** 而非 10.00：`BOX 1` 在 2024 年售价 9.00（现 10.00），阈值定高会漏。当前 `menu_item` 中 `price_1 ≥ 8.00` 的共 61 项，初始化时一次性归类入表即可，之后只报新增项。

**规则表应覆盖所有需要判断的项**（包括明确标记为「不是餐费、不计次」的项），巡检只提醒**尚未被规则表覆盖的新项**。这样人工确认过一次的项不会反复告警。

3. `menu_item` 全量缓存在本地，每日校准时刷新一次即可（数千行，非高频）

> 💡 **命名规律**：套餐 `item_id` = 价格 × 100（`2590`→25.90）。仅供人工识别，**不要在代码中依赖**。

> ✅ 历史数据不受菜单变更影响 —— `history_order_detail.menu_item_name` 保存的是下单时的名称快照。

### 5.4 交叉校验（取决于 POS 端操作方式）

> 🟡 **待确认**（`README.md` 事项 #4）：收银员在 POS 端如何免掉餐费？

| POS 端做法 | `discount_amount` 表现 | 我们能否兜底 |
|---|---|---|
| 整单/单项**折扣** | 变为负数（全库 4.79% 的单有折扣） | ✅ 可交叉校验："有大额折扣但 Pad 未核销"→ 报警 |
| **改价为 0** 或**删除该项** | 保持 0 | ❌ 无信号，只能靠 §5.2 的餐费项合计判据 |

## 6. 退单防刷

### 6.1 ⚠️ 不要用 `return_time` 增量扫描

**这会导致重复扣分。**

实测三条证据：

1. `history_order_head.return_amount` **全表 88,616 行恒为 0** —— 依赖它永不触发
2. 明细样本 14 条退菜行，`return_time` **100% 早于** `order_end_time`（订单 9934：退菜后 8 秒才结账）
3. 触发器 `trigger_history_order_detail_update`（明细被 UPDATE → head.status 置 1）在 **927 天里从未触发**（`status` 恒为 2）→ 历史明细归档后从不被修改

**结论**：历史表中的 `return_time` 全部是"结账前已发生"的退菜，其金额**已经从 `should_amount` / `actual_amount` 中扣除**（订单 9934 全单退 → `should_amount = 0.00`）。

按 `return_time` 扫到就扣分 = 对早已扣过的退菜**再扣一次**。

### 6.2 正确做法：值比对冲正

```
发分时：快照 total_amount 存入本地 pos_order
       ↓
校准时：按 (order_head_id, check_id) 单点回读主库当前金额
       ↓
    金额一致 → 无操作
    金额变小 → 按差额比例写冲正流水
    金额变大 → 记录告警，人工复核（不自动补分，避免被利用）
```

**优点：**

- **不依赖任何数据库自增 ID**（不用 `order_detail_id`），完全基于业务号 `serial_id`
- 覆盖面更广：不仅覆盖退菜，也覆盖 POS 的"修改历史账单"功能（实测 `edit_time` 显示 2,569 单/2.9% 在结账后被修改过，其中 1,144 单晚于结账 30 分钟以上）
- 开销更小：主键单点查，比扫 138 万行的 `idx_return_time` 轻得多

### 6.3 保护期

| 项 | 建议值 |
|---|---|
| 值比对保护期 | 发分后 **30 天** |
| 保护期内回读频率 | 每次校准任务执行 |
| 保护期外 | 不再回读，订单归档为最终状态 |

保护期内待比对订单量：30 天 × 95.6 单/天 ≈ **2,870 单** → `LIMIT 100` 分 29 批，批次间停顿 2 秒，约 1 分钟跑完。

### 6.4 冲正的积分处理

```
原积分 P，订单金额从 A 变为 A'（A' < A）
冲正积分 = P × (A - A') / A，向上取整（对商家有利）
```

若会员当前积分不足以扣除 → **允许负余额**并标记，下次消费优先抵扣。不阻断，也不静默丢弃。

## 7. 幂等与并发

### 7.1 幂等主键

```
(store_code, serial_id)
```

- `serial_id` 是 **POS 生成的业务流水号**（`YYMMDD` + 4 位），**非自增代理键** → 数据库迁移、重建、导入导出均不受影响
- `store_code` 为多店预留，写入配置文件，落库时一并记录
- **不使用** `order_head_id`（`AUTO_INCREMENT` 代理键）
- **不使用** `order_detail_id`（`AUTO_INCREMENT` 代理键）—— 值比对方案下根本不需要

> ⚠️ `serial_id` 的日期部分是**结账自然日**，不是营业日。作为幂等键完全可用；但**营业日统计必须按餐期规则自行计算**（实测 1,072 单为跨零点结账）。

### 7.2 并发保护

| 风险 | 对策 |
|---|---|
| 同一订单被两个 Pad 同时登记 | `pos_order` 行级锁 + 金额守恒约束在事务内校验 |
| 同一订单重复补抓 | `(store_code, serial_id)` 唯一约束，`INSERT ... ON DUPLICATE KEY UPDATE` |
| 撤销与新登记并发 | 撤销与登记走同一把行锁 |

### 7.3 本地库是唯一的幂等来源

主库只读，**无法在 POS 上打"已积分"标记**。因此：

> 🔴 **本地库一旦丢失或重装，会对历史订单重复发分。**

**备份策略（必须落实）：**

- 每日冷备 + **异地存储**（利用"仅出站"的网络策略推送到云端对象存储）
- 备份保留 30 天滚动
- 定期做恢复演练
- 备份文件加密（含会员 PII）

## 8. 营业日与餐期

后台可配置餐期，例：

| 餐期 | 时段 |
|---|---|
| 白天 | 11:00 – 18:00 |
| 晚上 | 19:30 – 次日 02:00 |

**实测营业时段佐证**：午市集中在 13:00–17:00（峰值 16 点 22,875 单），晚市 20:00–01:00（峰值 22 点 14,612 单），02:00–10:00 全时段 0 单。配置值留有充足余量。

**营业日归属规则**：跨零点的订单归属于**餐期起始日**。即 19:30 开始的晚市，其 00:30 结账的订单仍归属前一日。

> ⚠️ 不能直接取 `serial_id` 前 6 位当营业日 —— 它是结账自然日。必须按餐期规则重算。

**✅ 已用 POS 自己的数据验证**：拿 2024 年 332 个营业日，比对 `history_major_group.day`（POS 认定的营业日）与我们的归属结果 ——

| 归属口径 | 金额字段 | 完全一致 |
|---|---|---|
| 结账自然日 | `actual_amount` | 48 / 332 |
| **营业日（02:00 切点）** | **`original_amount`** | **324 / 332** |

全年总额差 -0.03%。切点取 02:00 / 04:00 / 06:00 结果完全相同（实测该区间 0 单）。详见 `01-POS主库数据字典.md` §5.2。

用途：积分按年/按日清零、等级保级周期计算、后台报表统计。

## 10. 🔴 数据缺失的降级预案

**`history_order_head` 不是 100% 可靠的数据源。** 实测发现真实的数据丢失事件：

> **2024-08-12 15:50 ~ 2024-08-18 23:40**，约 6 天、478 个订单号、**29,233.53 欧**的交易记录在 `history_order_head` 中不存在，但 `history_major_group` 的日汇总里有。
> 详见 `01-POS主库数据字典.md` §5.3。

### 10.1 影响

- 缺失期间收银员输桌号会**查不到任何订单**
- **校准任务无法自愈** —— 数据本来就不在主库里，补抓也抓不到
- 若无预案，这段时间的会员**全部无法积分**

### 10.2 降级流程

```
收银员输桌号 → 30 分钟窗口无结果
        │
        ▼
Pad 提示「未查询到订单」，提供两个选项：
        │
        ├─► ① 重试 / 放宽时间窗（后台可配，如临时放宽到 60 分钟）
        │
        └─► ② 手工录入积分
                · 收银员照小票输入金额
                · 强制填写原因（下拉：系统未查到 / 网络故障 / 其他）
                · 流水标记 source = manual，manual_reason
                · 不写入 pos_order（没有 serial_id），仅写 point_ledger
                · 自动进入后台「待复核」队列
```

### 10.3 手工录入的风控

| 措施 | 说明 |
|---|---|
| 权限 | 建议限经理或授权员工，普通服务员需授权码 |
| 金额上限 | 后台可配（如单笔 ≤ 200 欧），超出必须经理审批 |
| 频次告警 | 同一员工单日手工录入 > N 笔 → 后台告警 |
| 全部进复核队列 | 后台可按日导出，与纸质小票核对 |
| 审计 | 全部记入 `audit_log`，含操作人、设备、原因 |

### 10.4 数据完整性监控

日常校准任务中加一项检查：

```
若  某营业日的订单数 < 该店历史同星期几中位数的 50%
则  → 后台告警「疑似数据缺失」
```

基线参考：日均 95.6 单，P50 = 91，P95 = 159。

> 由于 `history_major_group` 自 2025 年起已停止写入（见 `01` §5.1），**不能再用它做日对账**。只能用订单数量的统计异常来发现缺失。

## 9. 校准任务总览

| 任务 | 频率 | 时段 | 内容 |
|---|---|---|---|
| 增量补抓 | 每 15–30 分钟 | 营业时间 | 从水位线起补抓新订单 |
| 滚动校准 | 48 小时窗口 | 03:00 – 05:00 | 补齐遗漏订单，循环至追上当前时间 |
| 值比对冲正 | 随滚动校准 | 03:00 – 05:00 | 回读保护期内订单金额，不一致则冲正 |
| 免费餐兜底 | 随滚动校准 | 03:00 – 05:00 | 餐费项合计=0 但未标记 → 报警 |
| 白名单巡检 | 随滚动校准 | 03:00 – 05:00 | `major_group=3` 且 `price>5.00` 的新项 → 提醒确认（§5.4） |
| 完整性监控 | 随滚动校准 | 03:00 – 05:00 | 单日订单数异常偏低 → 疑似数据缺失告警（§10.4） |

所有任务共用 `02-只读接入规范.md` 的五条铁律：命中索引、`LIMIT 100`、字段白名单、批次停顿、客户端超时。
