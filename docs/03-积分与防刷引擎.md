# 03 · 积分与防刷引擎

## 1. 订单定位

### 1.1 交互流程

```
收银员在 Pad 输入：
  ① 桌号（堂食）
  ② 会员标识 —— 三选一：卡号 / 完整手机号 / 邮箱（UI 上明确选择输入类型）
        │
        ▼
/app 查询 history_order_head（近 30 分钟 + 该桌号 + eat_type=0）
        │
        ▼
/app 侧按 order_head_id 聚合（同一订单的多张 check 合并求和）
        │
        ▼
Pad 展示候选订单：桌号 / 金额 / 人数 / 结账时间
        │
        ▼
收银员确认订单 → 选择记账方式 → 提交
```

### 1.2 为什么必须按 `order_head_id` 聚合

实测 76,523 笔可积分订单（堂食 + `actual_amount > 0`），模拟"结账后 1/5/10/15/20/25/30 分钟查询"共 53 万次：

| 返回方式 | 窗口 15 分 | 窗口 30 分 | 窗口 45 分 | 窗口 60 分 |
|---|---|---|---|---|
| 按 check 行直接返回 | 10.36% | **10.95%** | 11.61% | 11.81% |
| **按 `order_head_id` 聚合后返回** | 0.01% | **0.02%** | 0.06% | 0.23% |

**歧义主因拆解（30 分钟窗口）**：同一订单分单造成 **8,873** 次，真正翻台造成的仅 **14** 次。

> 结论：歧义几乎全部来自"同一桌同一单的多张 check"，聚合后即消失。53 万次模拟中仅 127 次返回 2 条订单，此时 Pad 展示金额让收银员点选即可。

### 1.3 窗口时长

- 后台可配置，**默认 30 分钟**
- 窗口拉长收益极小（15→60 分钟，聚合后歧义仅从 0.01% 升到 0.23%），但会增加误选风险
- 时间基准**必须**用主库 `NOW()`

### 1.4 外带订单

**外带（`eat_type = 3`，占 11.84%）不积分。**

原因：全部 10,495 单的 `table_name` 恒为 `'Llevar'` / `'Paquetear'`，桌号定位歧义率高达 81.40%，无法可靠识别。

实现上用**白名单** `eat_type = 0`，不要写 `eat_type != 3`（库中还有 `eat_type = 1`(3单)、`= 2`(4单) 来路不明的记录，白名单可自动排除）。

## 2. 积分基数

```
积分基数 = LEAST(should_amount, actual_amount)
```

在 `/app` 侧计算，不在 SQL 内计算。

| 场景 | should | actual | 基数 | 说明 |
|---|---|---|---|---|
| 正常消费 | 58.30 | 58.30 | 58.30 | 两者相等 |
| 现金抹零 | 211.70 | 215.00 | **211.70** | 多付的 3.30 是小费，不计入 |
| 10送1 免费餐 | 0.00 | 0.00 | **0.00** | 不积分 |
| 员工餐/招待 | 0.00 | 0.00 | **0.00** | 不积分 |

### 2.1 含税说明

`actual_amount` 为**含 IVA 10% 的实付额**（实测 `SUM(tax)/SUM(should) = 9.09% = 10/110`）。

**积分按含税价计算** —— 已确认。

### 2.2 硬性过滤条件

```
可积分 = (eat_type == 0)
       AND (LEAST(should_amount, actual_amount) > 0)
       AND (未被标记为免费餐)
```

`actual_amount = 0` 的订单共 1,666 单（1.88%，按月均匀分布 40~78 单），**既不积分也不计次**。

## 3. 记账方式（服务员选择）

同一订单可被**多个会员**分别积分，三种模式由服务员在 Pad 上选择：

### 模式 A —— 整单记给一人

```
会员 X 获得：金额 = 订单全额，次数 +1
```

### 模式 B —— 均摊 AA

```
Pad 上输入人数 N（默认取 history_order_head.customer_num）
每人金额 = 订单全额 / N
```

- 除不尽时，**余数分配给第一位会员**（保证 `SUM(分摊) == 订单全额`，分毫不差）
- 允许只登记其中部分人（如 4 人 AA 但只有 3 人有卡），剩余份额保持未分配状态

### 模式 C —— 点选菜品

读取 `history_order_detail`，让每位会员认领自己点的菜。

**⚠️ 套餐店特殊性**：这家店 86.9% 的菜品单价为 `0.00`（套餐内无限点）。真正有金额的只有**套餐主项**（`MENÚ INFINITY = 23.90` 等）和**饮料酒水甜点**。

#### 3.C.1 显示规则

Pad 上**只显示有金额的项**，套餐内的 0 元菜品不显示（列表太长、且不影响分摊）。

**但有一个必须处理的特例**：当套餐本身被免费时（10送1 那一次），`MENÚ INFINITY` 的实收金额也是 `0.00`。若按"只显示有金额的项"直接过滤，享用免费餐的那位客人在列表里**什么都认领不到**。

**判据**（不依赖分组白名单）：明细表的三个价格字段能区分两种 0 元 ——

| `product_price` | `original_price` | `actual_price` | 含义 | 显示 |
|---|---|---|---|---|
| `0` | `NULL` | `0` | **套餐内菜品**（本来就免费） | ❌ 隐藏 |
| `>0` | `NULL` | `>0` | 正常收费项 | ✅ 显示 |
| `>0` | `NULL` | **`0`** | **被免的收费项**（伴随 `is_discount = 1`） | ✅ **显示** |
| `0` | **`>0`** | `0` | **被免的收费项**（另一种记法） | ✅ **显示** |

```
显示 = (actual_price > 0) OR (product_price > 0) OR (original_price > 0)
隐藏 = 三者全为 0 / NULL
```

被免的收费项**总会在 `product_price` 或 `original_price` 上保留原价痕迹**（实测：`Agua` 原价 2.80 实收 0、`Verdejo` 原价 13.95 实收 0），而套餐内菜品三个字段全为 0/NULL。

> 📊 **样本说明**：该判据基于 100 行明细样本（4 种组合分别为 68 / 6 / 4 / 2 行）。组合分布清晰但样本量小，**建议上线前用更大样本（如近 30 天明细）复验一次**，确认没有第五种组合。

#### 3.C.2 UI 要求

- 被免的项（实收 0 但有原价）→ 显示时标注 `原价 23.90 → 已免`，让客人看得懂
- 有价项视觉突出（加粗/标金额）
- 实际效果：每人认领自己那份 MENÚ 套餐 + 自己的酒水，天然形成 AA；享用免费餐的那位也能正常认领

**明细过滤**（见 `02-只读接入规范.md` §3.4）：

```
menu_item_id > 0            排除 -3 备注行、-4 支付方式行
condiment_belong_item = 0   排除配料/做法行
is_return_item + 0 = 0      排除已退菜行
三个价格字段全为 0/NULL      排除套餐内菜品（仅影响显示，不影响金额计算）
```

### 3.1 金额守恒约束

无论哪种模式，恒定成立：

```
SUM(point_ledger.amount WHERE serial_id = X 且未撤销)  ≤  pos_order.total_amount
```

每次积分前校验 `allocated_amount + 本次金额 ≤ total_amount`，超出即拒绝并提示"该订单已全额积分"。

### 3.2 计次规则

> 🔴 **待确认**（`README.md` 事项 #2）：AA 时 3 人分摊一餐，是**每人各 +1 次**，还是**整单只算 1 次**？
>
> 倾向建议：**每人各 +1 次**（每人确实吃了一餐）。但需注意商业影响——3 人 AA 吃 10 次即可换 3 顿免费餐。
>
> 当前实现预留 `counted_visit` 字段（每条流水独立标记是否计次），后台开关切换两种策略，确认后调整默认值即可。

## 4. 撤销

### 4.1 设计原则：追加式账本（Append-only）

**撤销 = 写一条反向冲正流水，绝不物理删除原流水。**

理由：
- 西班牙会计/税务留存义务
- 全流程可审计
- 避免并发删除导致的金额守恒破坏

```
原流水:  id=101  member=A  amount=+58.30  points=+58  status=active
撤销后:  id=101  member=A  amount=+58.30  points=+58  status=reversed  reversed_by=102
         id=102  member=A  amount=-58.30  points=-58  type=reversal    reverses=101
```

同时 `pos_order.allocated_amount` 回退，订单状态从 `fully_allocated` 回到 `open`，可重新分配。

### 4.2 典型场景

> 服务员先把整单记给了一个人，客人说要分别记给每一个人，且其中一位客人还没有卡。

流程：

```
1. 服务员在 Pad 调出该订单（按桌号或会员近期流水）
2. 点击"撤销记账" → 系统写冲正流水，订单回到 open 状态
3. 服务员改选"均摊 AA"，输入人数
4. 对没有卡的客人 → 内联"新增会员"（见 §4.4）
5. 逐个登记，直到分配完毕
```

### 4.3 撤销的约束

| 项 | 建议值 | 状态 |
|---|---|---|
| 时间窗 | 当班内（营业日内）可自由撤销 | 🟡 待确认 |
| 超时窗后 | 需经理权限 | 🟡 待确认 |
| 权限 | 服务员可撤销自己当班登记的；跨班/跨日需经理 | 🟡 待确认 |
| 已消费积分 | 若积分已被兑换，撤销会导致负余额 → **允许负余额并标记**，不阻断撤销 | 建议 |
| 审计 | 每次撤销记录操作人、时间、原因 | 必须 |

### 4.4 内联新增会员（配合 LOPDGDD）

积分流程中可直接创建会员，但必须走合规路径：

```
新建会员 → 状态 pre_registered
        → 积分正常入账，标记 consent_status = pending
        → 系统立即发送 double opt-in 短信/邮件（含隐私政策链接）
        → 客人点击同意 → 状态 active，积分解冻可用
        → N 天（默认 30）未同意 → 积分冻结 + PII 假名化
```

**关键**：积分**当场就要入账**（客人马上要走），但在同意前**不可用于兑换、不可用于营销推送**。详见 `05-合规与Wallet.md`。

## 5. 免费餐（10送1）识别

### 5.1 主路径：Pad 端核销标记

10送1 的核销**本来就发生在侧系统**，我们自己知道：

```
收银员在 Pad 点击"使用免餐券"
     → 本地标记该 serial_id 为 is_free_meal = 1
     → 该单不计次
     → 额外消费（饮料甜品）是否计入金额积分：后台开关控制
     → 收银员再到 POS 端手动做对应折扣收银
```

**不依赖 POS 判断。**

### 5.2 兜底：防止收银员漏点

风险：收银员忘了在 Pad 点核销，直接在 POS 打折 → 我们当成正常消费计次了。

**兜底校验**（校准任务中执行），分两层：

**第一层 —— 「被免金额」信号（不需要白名单，可立即上线）**

利用 §3.C.1 的价格字段判据，订单级计算：

```
被免金额 = SUM( COALESCE(NULLIF(original_price,0), product_price) - actual_price )
           WHERE 该差值 > 0

若  被免金额 > 0
且  本地未标记 is_free_meal
则  → 后台报警，人工复核
```

> ⚠️ 这一层会同时捕捉到**普通赠送**（送一瓶水 2.80）和**免餐券**（免掉 23.90 的套餐），需要按金额量级设阈值，或用第二层精确区分。

**第二层 —— 「餐费项合计」精确判据（需要白名单）**

```
若  订单的「餐费项」金额合计 == 0
且  订单 LEAST(should, actual) > 0        ← 说明只剩饮料甜品的钱
且  本地未标记 is_free_meal
则  → 后台报警，人工复核
```

> ⚠️ **绝不能用"单行 `actual_price = 0`"判断**。这家店 86.9% 的菜品单价本来就是 0（套餐内无限点），按单行判断会把每一单都误判成免费餐。必须用**订单级的餐费项合计**。

### 5.3 「餐费项」白名单

> 🟡 **待补**（`README.md` 事项 #1）：需要 `major_group` / `family_group` 两张表的数据以确定分组名称。
>
> **不阻塞上线** —— §3.C.1 的价格字段判据已让 AA 点选菜品 UI 与第一层兜底校验都能正常工作。白名单只用于把兜底校验从"被免金额 > 0"精确到"被免的确实是套餐主项"，降低误报。

已知分组结构（见 `01-POS主库数据字典.md` §4）：

| family / major | 内容 | 是否算餐费 |
|---|---|---|
| `family=8, major=3` | `MENÚ INFINITY=23.90`、`MENÚ DEL DIA=15.90`、`INFANTIL=12.90` | ✅ 是 |
| `family=8, major=3` | `Tenedor`、`Wasabi`、`Suplemento`（同组混入） | ❌ 否 |
| `family=1, major=2` | `Agua=2.95`、`Verdejo=13.95`、`Tiramisú=5.95` | ❌ 否（饮料甜点） |
| `family=3/4/5/7/9, major=1` | 套餐内菜品（86.9% 为 0 元） | ❌ 否 |

由于 `family=8, major=3` 组内混有餐具调料，**不能整组当餐费**。

**落地方式**：后台维护一张「餐费项 `menu_item_id` 白名单」，菜单变动时人工维护。拿到分组数据后即可预填。

### 5.4 交叉校验（取决于 POS 端操作方式）

> 🟡 **待确认**（`README.md` 事项 #4）：收银员在 POS 端如何免掉餐费？

| POS 端做法 | `discount_amount` 表现 | 我们能否兜底 |
|---|---|---|
| 整单/单项**折扣** | 变为负数（全库 4.79% 的单有折扣） | ✅ 可交叉校验："有大额折扣但 Pad 未核销"→ 报警 |
| **改价为 0** 或**删除该项** | 保持 0 | ❌ 无信号，只能靠 §5.2 的餐费项合计判据 |

## 6. 退单防刷

### 6.1 ⚠️ 不要用 `return_time` 增量扫描

**这会导致重复扣分。**

实测三条证据：

1. `history_order_head.return_amount` **全表 88,616 行恒为 0** —— 依赖它永不触发
2. 明细样本 14 条退菜行，`return_time` **100% 早于** `order_end_time`（订单 9934：退菜后 8 秒才结账）
3. 触发器 `trigger_history_order_detail_update`（明细被 UPDATE → head.status 置 1）在 **927 天里从未触发**（`status` 恒为 2）→ 历史明细归档后从不被修改

**结论**：历史表中的 `return_time` 全部是"结账前已发生"的退菜，其金额**已经从 `should_amount` / `actual_amount` 中扣除**（订单 9934 全单退 → `should_amount = 0.00`）。

按 `return_time` 扫到就扣分 = 对早已扣过的退菜**再扣一次**。

### 6.2 正确做法：值比对冲正

```
发分时：快照 total_amount 存入本地 pos_order
       ↓
校准时：按 (order_head_id, check_id) 单点回读主库当前金额
       ↓
    金额一致 → 无操作
    金额变小 → 按差额比例写冲正流水
    金额变大 → 记录告警，人工复核（不自动补分，避免被利用）
```

**优点：**

- **不依赖任何数据库自增 ID**（不用 `order_detail_id`），完全基于业务号 `serial_id`
- 覆盖面更广：不仅覆盖退菜，也覆盖 POS 的"修改历史账单"功能（实测 `edit_time` 显示 2,569 单/2.9% 在结账后被修改过，其中 1,144 单晚于结账 30 分钟以上）
- 开销更小：主键单点查，比扫 138 万行的 `idx_return_time` 轻得多

### 6.3 保护期

| 项 | 建议值 |
|---|---|
| 值比对保护期 | 发分后 **30 天** |
| 保护期内回读频率 | 每次校准任务执行 |
| 保护期外 | 不再回读，订单归档为最终状态 |

保护期内待比对订单量：30 天 × 95.6 单/天 ≈ **2,870 单** → `LIMIT 100` 分 29 批，批次间停顿 2 秒，约 1 分钟跑完。

### 6.4 冲正的积分处理

```
原积分 P，订单金额从 A 变为 A'（A' < A）
冲正积分 = P × (A - A') / A，向上取整（对商家有利）
```

若会员当前积分不足以扣除 → **允许负余额**并标记，下次消费优先抵扣。不阻断，也不静默丢弃。

## 7. 幂等与并发

### 7.1 幂等主键

```
(store_code, serial_id)
```

- `serial_id` 是 **POS 生成的业务流水号**（`YYMMDD` + 4 位），**非自增代理键** → 数据库迁移、重建、导入导出均不受影响
- `store_code` 为多店预留，写入配置文件，落库时一并记录
- **不使用** `order_head_id`（`AUTO_INCREMENT` 代理键）
- **不使用** `order_detail_id`（`AUTO_INCREMENT` 代理键）—— 值比对方案下根本不需要

> ⚠️ `serial_id` 的日期部分是**结账自然日**，不是营业日。作为幂等键完全可用；但**营业日统计必须按餐期规则自行计算**（实测 1,072 单为跨零点结账）。

### 7.2 并发保护

| 风险 | 对策 |
|---|---|
| 同一订单被两个 Pad 同时登记 | `pos_order` 行级锁 + 金额守恒约束在事务内校验 |
| 同一订单重复补抓 | `(store_code, serial_id)` 唯一约束，`INSERT ... ON DUPLICATE KEY UPDATE` |
| 撤销与新登记并发 | 撤销与登记走同一把行锁 |

### 7.3 本地库是唯一的幂等来源

主库只读，**无法在 POS 上打"已积分"标记**。因此：

> 🔴 **本地库一旦丢失或重装，会对历史订单重复发分。**

**备份策略（必须落实）：**

- 每日冷备 + **异地存储**（利用"仅出站"的网络策略推送到云端对象存储）
- 备份保留 30 天滚动
- 定期做恢复演练
- 备份文件加密（含会员 PII）

## 8. 营业日与餐期

后台可配置餐期，例：

| 餐期 | 时段 |
|---|---|
| 白天 | 11:00 – 18:00 |
| 晚上 | 19:30 – 次日 02:00 |

**实测营业时段佐证**：午市集中在 13:00–17:00（峰值 16 点 22,875 单），晚市 20:00–01:00（峰值 22 点 14,612 单），02:00–10:00 全时段 0 单。配置值留有充足余量。

**营业日归属规则**：跨零点的订单归属于**餐期起始日**。即 19:30 开始的晚市，其 00:30 结账的订单仍归属前一日。

> ⚠️ 不能直接取 `serial_id` 前 6 位当营业日 —— 它是结账自然日。必须按餐期规则重算。

用途：积分按年/按日清零、等级保级周期计算、后台报表统计。
