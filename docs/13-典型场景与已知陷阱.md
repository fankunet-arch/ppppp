# 13 · 典型场景与已知陷阱

> 🔴 **改动奖励、计次、撤销、手工录入这几块之前，先看这份。**
>
> 前面的文档讲「系统怎么设计的」，这一份讲两件别处没有的事：
>
> * **柜台上真会发生什么** —— 客人问什么、系统怎么答、服务员该怎么说；
> * **我们已经踩过哪些坑** —— 现象、根因、现在靠什么守住、测试在哪一行。
>
> 第三节那张表不是流水账。这套系统前后六轮审计查出 30 多个缺陷，
> 其中**相当一部分是「修了被点名的那一处、没修这一类」**。
> 把它们按类型归档，是为了让下一个人（也包括下一次的我）
> 在写下同样形状的代码之前先认出来。

## 一、柜台上会遇到的场景

### 1.1 同一餐期，客人又开了一单

> 一桌吃完结了账，又加点甜点酒水另开一单。服务员照常拿卡去记。

`visit_count_mode = once_per_period` 下**一张卡一个餐期最多计 1 次**，
所以第二单**照样记得上**（金额进账），但**计次是 0**。

| 积分口径 | 第二单的结果 | 服务员该怎么说 |
|---|---|---|
| `by_amount`（默认） | 计次 0，**积分照给** | 「这一单不攒次数，但积分照记」 |
| `by_visit` | 计次 0，**一分都没有** | 「这一单不攒次数，也不加分」 |

🔴 **这件事必须在【记账之前】说。** Pad 上有两处：

* **选完会员** → 那一行挂一条常驻黄色提示（服务员要拿着这句话去跟客人说，
  而他往往是先选人、再算金额、再回头解释，弹一下就没的东西用不上）；
* **点提交** → 弹一次页内确认，正文写明「请先告知客人」，
  按钮是「返回修改 / 仍然记账」。点返回修改就是真的什么都没记。

> ⚠️ 正常单**一次都不打扰**。每单都弹的确认框，三天之后就变成闭着眼睛点「继续」。

详见 `03` §3.7。

---

### 1.2 服务员拿错卡，正好把客人凑满了门槛

> 客人已经攒到 9 次。服务员把别桌的账记到他名下 —— 正好 10 次，
> 系统当场发了一张免费餐券。经理随后发现。

**两种情况的正确结局不一样**，系统分开处理：

#### A · 券还没用掉 → 撤销就把它收回

```
撤销之前   计次 10 · 已发 1 · 券 可用
撤销之后   计次  9 · 已发 0 · 券 已作废
```

**客人后来自己真的吃到第 10 次时，照常拿到那张券。**

> 🔴 这里曾经有过一个很难发现的坑：撤销只退计次不退「已发计数」，
> 于是 `应发 − 已发` 永远算出 0，**客人白白少一张**，
> 而进度条上写着「还差 10 次」，看上去完全正常，谁也不会觉得不对。

#### B · 客人已经把券吃掉了 → 那顿饭收不回来

```
撤销之后   计次 9 · 已发 1 · 券 保持「已核销」
           ＋ 挂告警 reward_on_reversed_grant（severity 2）
```

* **券的状态不动** —— 饭已经吃了；
* **已发计数不退** —— 客人确实拿到了那份奖励，退了他会再拿一张；
* **必挂告警** —— 这是一份发错的账换来的免费餐，经理必须知道，否则连账都没地方对。

客人后来真的吃到第 10 次时**不再发券**。
账是平的：10 次真实消费 → 1 顿免费餐（就是已经吃掉的那顿）。

> **客人可能会问「我满 10 次了怎么没券」**。
> 正确答复：那一顿免费餐您已经用过了（当时是记错账提前发的）。
> 后台的告警和审计里查得到是哪一笔、谁记的。

#### 作废的券不会复活

作废掉的券**不会**在后续消费中自己翻回可用，
**经理用 force 也核销不掉**（状态检查排在 force 分支之前）。

实测：`tests/smoke.php` ㊺。

### 1.3 POS 侧改单或作废了

夜间值比对（`ReconcileService`）发现订单金额变了，会退回相应的积分、计次、消费额，
**券也跟着退**。

| 情况 | 计次 | 券 |
|---|---|---|
| 部分退菜（金额缩水） | **不动**（那顿饭确实吃了） | 按新进度重算，多出来的收回 |
| 整单归零 | **退回** | 收回 |

> 🔴 曾经的坑：撤销那条路会收券，**值比对这条路一个字没碰券**。
> 而 POS 侧改单作废是店里天天发生的事，手工撤销反而是少数 —— 漏的恰好是常走的那条。

**打错单 → 作废 → 同一餐期重打一张**：重打的那单**正常计次**。
（原始流水会被标记成已冲正、退出风控视野，否则它会一直占着「本餐期已记过」的位置，
客人真吃了一顿却一次都没有。）

详见 `03` §7.5、§7.6。

---

### 1.4 POS 查不到订单（手工录入）

POS 挂了或查不到单时，收银员可以照小票手工录入金额。这条路**必须留着** ——
堵死它等于把正常客人一起挡在门外。但它没有 POS 订单作证，所以：

| | |
|---|---|
| **计次** | 恒为 **0** —— 手工录入证明得了「这个人花了钱」，证明不了「他吃了几份套餐」 |
| **积分** | 照给。`by_visit` 口径下按【一次】算，否则 POS 挂掉时这条路永远 0 分，等于废掉 |
| **单笔下限** | `manual_entry_min`（出厂 1.00）。`by_visit` 下自动抬到与「计一次至少多少钱」的较大值 |
| **单笔上限** | `manual_entry_limit`（200.00）以上要经理放行；`manual_entry_hard_limit`（5000.00）谁都不行 |
| **日累计上限** | `manual_entry_daily_cap`（300.00），按**营业日**切，**经理也不能放行** |
| **留痕** | 全部进「待复核」队列 + 审计；单日笔数超阈值告警 |

> 🔴 **按金额发券时**，手工录入会直接推高奖励进度。所以发券那一刻，
> 若该会员的手工录入金额本身已够一个门槛，必留一条 `reward_from_manual_entry` 告警 ——
> **造出免费餐的那一刻永远不是静默的。**

---

### 1.5 客人用券吃免费餐那一次

* **不计次** —— 兑换来的一餐不该再攒一次；
* 额外点的酒水甜点算不算积分，由 `free_meal_extra_earns` 决定（出厂**关**）；
* 关着的时候这类单在选单页就是**灰的、点不动**，
  Pad 上不会显示「不计次」这种误导的话（那会让服务员以为「别的照记」，
  而实际是一分钱都记不进去）。

---

### 1.6 同行分桌 vs 捡小票

这两件事在系统里长得一模一样（多张订单记进同一张卡），
能把它们分开的**只有时间**：

* 同行分桌永远是当场、几分钟内，几张单的结账时间也挨着；
* 捡小票在物理上必须发生在结账之后，而且小票来源分散。

所以风控参数全是**时间**参数，不是数量参数。详见 `03` §12。

---

### 1.7 两台 Pad 同时记账

支持。但**加锁顺序必须固定** —— 两桌客人里有同两位老顾客（一对夫妻、
常一起来的朋友，小店里天天有），只要两台 Pad 点人的顺序不同就会互相锁死。

实测不固定顺序时：4 个进程 320 单里**死锁 172 次（53.8%）**，
收银员看到的是「本地数据库暂时不可用，请联系管理员」—— 而库好得很。

现在三道：固定加锁顺序（`sort($lockIds)`）、事务自动重放、
死锁单独归 `E110` 并提示「请再点一次提交（不用找管理员）」。

---

### 1.8 卡片相关

| 情况 | 系统怎么处理 |
|---|---|
| 卡快到期 | 每次扫到都提醒换卡，但点「稍后再说」照常用 —— 不记「已读」，否则最后一次提醒之后就再没人提 |
| 卡已过期 | 不是死路，直接引导换卡；积分、计次、未兑换的券全部结转 |
| 换卡 | 只换 `card` 行，`member_id` 不变 → 流水与券天然跟着走 |
| `card_prefix` 配错 | **只停发卡与查卡**，找单、记账、撤销、手工录入照常 —— 收银台不能因为卡号少个连字符就整个停摆 |

## 二、我们特意做过取舍的地方

这一节记的是**「为什么是这样而不是那样」**。
改动前先看一眼，很多"顺手优化"其实会踩掉某个刻意的设计。

| 决定 | 为什么 |
|---|---|
| 撤销**收回**没用掉的券，但**不动**已核销的 | 饭已经吃了，收不回来。硬把已发计数减掉，客人会再拿一张 |
| 手工录入**给分不计次** | 它证明得了花钱，证明不了吃了几份套餐。而计次直接换免费餐 |
| 门槛调低会**回溯补发** | 达标判定是自愈式的（应发 − 已发），改门槛能自动对上、不重不漏。代价是调低那一刻会按历史进度补发 —— 所以要算出张数并留痕，但**不拦**（店家有权促销） |
| `by_visit` 下同餐期第二单**一分都没有** | 那是「一次积一分」的定义，不是漏算。所以界面措辞必须跟着口径换 |
| 券的有效期**写在券上** | 客人拿到手的券，到期日就不该再变。之后改规则只影响新发的 |
| 小票号查单**含糊其辞** | 小票号是连号整数，精确的答复等于给人一个可枚举的预言机。经理也只给「在期内 / 在期外」二值 |
| **不**阻止 pad 息屏 | 店里明确要求省电 |
| 值比对发现订单在 POS 消失时**不自动扣分** | 推 `order_vanished` 告警等人工核实 —— 消失可能是 POS 侧的问题，不该让客人替它买单 |
| 内部人作案**不做事前拦截** | 能拿到收银机的就是店里的人，事前拦在结构上无效。能做的是：**框住上限 + 保证不静默** |

## 三、已经踩过的坑

> 按**类型**归档，不按时间。同一类里只要认出一条，剩下的就能自己发现。

### 3.1 「修了那一处，没修那一类」

**最高频的一类。** 每一条都是同一个缺陷在另一条路上又出现一遍。

| 现象 | 根因 | 现在靠什么守住 |
|---|---|---|
| 撤销会收券，**值比对不会** | 只在 `reverseInTx` 加了 `clawBackOverIssued`，忘了 `applyShrink` | 两条路调**同一个**方法；smoke ㊵ |
| 「份数必须带金额」只堵住 0 元，0.01 元照过 | 只想到「0 元白拿」这一个形状 | `min_amount_per_visit`；smoke ㊲ |
| 门槛判据没乘份数，`by_portion` 下被稀释 N 倍 | 判据写成「每笔分配」，而名字是「计**一次**」 | 判据 `× $prt`；**AllocationTest 穷举性质** |
| 回溯补发的护栏只认两个键 | 钉在「改了哪个键」上，而换口径、改等级门槛都绕得过去 | 改成**保存前后各量一次**，变多就报警 |
| 日累计上限按日历零点切 | 这套系统里只有它自己搞了一套「一天从几点开始」 | 走 `BusinessDay::range()` |

> 🔴 **认出这一类的方法**：修完一个缺陷，先问
> **「同样形状的代码还有几处？」** 而不是「测试过了吗」。

### 3.2 静默的钱

| 现象 | 根因 |
|---|---|
| 门槛填 `0` → 一位 10 次的会员当场发出 10 张 | `max(1,…)` 静默兜住，不报错 → 变成「每来一次送一次」 |
| 换积分口径 → 待补发 0 跳到 37 张，界面无提示、告警一条没有 | 护栏看不见这条路 |
| 手工录入 3 笔 200 → 6 张免费餐券 | 日风控只数**笔数**，笔数管不住钱 |
| 撤销把日额度算成 **−300** → 一个班次录进 600 | 统计没按 `entry_type` 过滤，撤销那条负数流水的 `source` 也是 MANUAL |

> 🔴 **认出这一类的方法**：任何一处能让**券的数量变多**的代码，
> 问一句 **「这件事发生时，有人会知道吗？」**

### 3.3 时间与时区

| 现象 | 根因 |
|---|---|
| 券的有效期跨夏令时**差一天**（Madrid 全年 3285 组里错 550 组） | `+N × 86400 秒` 不等于 `+N 个日历天`，而晚市 00:xx 发券是常态 |
| 营业日跨度在切换日错开一小时 | 止点用了「起点 + 1 天」而不是「下一个营业日的起点」 |
| 日累计上限在班次中间被清零 | 用日历零点，而营业日切点是 02:00 |

> 🔴 **认出这一类的方法**：看到 `86400`、`date('Y-m-d 00:00:00')`、`+1 day`，
> 停下来问 **「这里说的『一天』，是日历日还是营业日？跨夏令时会怎样？」**

### 3.4 并发

| 现象 | 根因 |
|---|---|
| 两台 Pad 交叉点人 → 53.8% 的单记不进去 | `grantOne` 按客户端给的顺序锁会员行 |
| 并发 `checkAndGrant` 多发券 | 曾经是「读 → 算 → 发 → 加计数」四步裸奔 |
| 事务重放导致发卡清单重复 | 闭包按引用捕获 `&$out`，库里的行回滚了它回滚不掉 |

> 🔴 **`php -S` 默认单进程，并发缺陷在本地结构性地复现不出来。**
> 现场跑 PHP-FPM，天然多进程 —— **开发环境比生产环境更宽容，
> 而且宽容的正好是最难查的那一类。**
> 跑探针要带 `PHP_CLI_SERVER_WORKERS=8`；真正的并发断言在 smoke ㉖ / ㊱，它们自己 fork 进程。

### 3.5 前后说两套话

| 现象 | 根因 |
|---|---|
| 预览说「只是不计次」，实际整单拒绝 | `visitPreview` 漏看 `free_meal_extra_earns` |
| 死锁提示「数据库不可用，请联系管理员」 | 1213 落进了「连不上」那一档，而它其实重试就好 |
| 结果页大字是「+87 分」 | 客人真正在数的是「我来了几次」，分是个要换算的数字 |

> 🔴 **认出这一类的方法**：任何给人看的话，问一句
> **「照着这句话做，会得到它说的结果吗？」**

### 3.6 测试本身的坑

| 现象 | 教训 |
|---|---|
| `?>` 写在 `//` 注释里，悄悄吃掉最后 8 条断言，测试**照样全绿** | 加了元断言扫描 `cases/*.php` |
| smoke 自己算券到期日**也用旧公式** —— 两边一起错正好抵消，永远绿 | 期望值不能复用被测代码的算法 |
| 服务层探针跑得好好的，一走路由**每次保存都 500** | `ConfigRepo::get()` 第二个参数不可为 null。**服务层探针不走路由，抓不到这一类** |
| 浏览器测试中断后残留污染下一次运行，报出的错与真问题无关 | 测试开跑前先清自己往次的残留 |

## 四、加新功能时的自检清单

> 这一节是上面三节的浓缩。**动奖励、计次、撤销、手工录入之前逐条过一遍。**

**钱**

- [ ] 这个改动会不会让**券的数量变多**？变多的那一刻，有人会知道吗？
- [ ] 有没有第二条路能达到同样的效果？（换口径、改等级、改开关…）
- [ ] 「上限」类的东西：**超了谁能放行？** 如果答案是「最可能滥用的那个人」，那它就不是上限。

**同一类**

- [ ] 我刚修的这个缺陷，**同样形状的代码还有几处**？（`grep` 一遍，别只改被点名的那处）
- [ ] 两条路径对同一件事，给出的是**同一个结果**吗？

**时间**

- [ ] 代码里的「一天」是日历日还是**营业日**？（切点 02:00，晚市跨零点）
- [ ] 跨**夏令时**那两天会怎样？

**并发**

- [ ] 多行加锁：顺序固定了吗？
- [ ] 事务闭包**跑两遍**结果还对吗？（重放会发生；按引用捕获的变量回滚不掉）

**说人话**

- [ ] 界面上这句话，**照着做会得到它说的结果**吗？
- [ ] 报错是把人指向**该去查的地方**，还是指向一个没问题的地方？

**测试**

- [ ] 断言的是**性质**还是**我想到的那个场景**？
  （逐个场景永远追不上没想到的组合 —— 见 `AllocationTest` 的穷举写法）
- [ ] 期望值是**独立算出来的**，还是复用了被测代码？
- [ ] 路由层的东西，**真的打过一遍接口**吗？

## 六、上线前的建议：影子模式

前六轮审计共查出 30 多个缺陷，其中会造成**餐费损失**的有 8 条 ——
每一条都不是靠「想清楚」发现的，都是靠**实测**。

所以上线的第一个月，建议：

```
reward_auto_grant = 0        自动发券关掉
```

记账、计次、积分全部照常跑，只是**券不自动发** ——
达标的客人进后台「待发」队列，由经理逐张确认后发出。

这样任何异常（不该达标的人达标了、张数不对、进度跳变）
都会在**变成一顿免费餐之前**先被人看见一眼。

跑满一个月、后台待发队列里没有出现过说不清的条目，再打开自动发放。
