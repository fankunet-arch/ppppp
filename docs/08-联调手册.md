## 阶段零 · 先在 PC 浏览器上确认 Web 是好的

**平板出问题时，第一件事是排除 Web 侧。** 在店内任意一台 PC 上：

### 0.1 服务活着吗

浏览器打开：

```
https://lms.sushisom.net/api.php/health
```

| 看到什么 | 说明 |
|---|---|
| `{"ok":true,"data":{"local_db":true,"pos_db":true,...}}` | ✅ 正常，继续 |
| `{"ok":true,...,"local_db":false}` | 本地会员库连不上 |
| `{"ok":false,...,"错误代码 B001-XXXXXX"}` | 部署目录被 PHP 挡住（open_basedir） |
| 一段 HTML / PHP 报错 | 服务端 fatal，把首屏文字发给开发 |
| 打不开 | 服务没起来，或 DNS / 网络问题 |

### 0.2 能登录、能查单吗

打开 `https://lms.sushisom.net/`，用收银员工号登录，随便查一张单。
**这一步过不了就不用碰平板了**，先修 Web。

## 阶段一 · 平板能不能打开页面

装好 APK，直接开。

| 现象 | 原因 | 谁来修 |
|---|---|---|
| 正常显示登录页 | ✅ 继续下一阶段 | — |
| **白屏，什么都没有** | 多半是证书不受信任 | APK 侧 |
| 弹「网络未连接」 | 平板没连上 Wi-Fi | 门店 |
| **熄屏一会儿再打开就要求重新登录** | Android WebView 的 Cookie 默认只在内存里，熄屏后进程被回收就丢了（要 `CookieManager.flush()` 才落盘）。**Web 侧已兜底**：令牌同时存一份进 localStorage，请求带 `X-Session-Token` 头。容器侧的加固见本文档「给容器（APK）工程师的加固清单」。🔴 **不要用「阻止息屏」来回避** —— 门店要省电，会话必须扛得住息屏 | 已修 |
| 弹「无法解析服务器地址」 | 平板 DNS 解析不了 `lms.sushisom.net` | 门店路由器 |
| 显示 App 内置的错误页 | 上面有具体原因，照着念 | 看原因 |

> 白屏最常见的原因是自签证书没被信任。APK 里已经打包了
> `res/raw/intranet_ca.crt`，如果换过证书而没换这个文件，就会白屏。

## 阶段二 · 用 `diagnose()` 一次看清所有状态 ⭐

**这是最重要的一步，几乎所有问题都能在这里定位。**

### 怎么执行

1. 平板用 **USB 线**连到一台电脑（平板上若弹「允许 USB 调试」，选允许）
2. 电脑上打开 **Chrome**，地址栏输入：`chrome://inspect`
3. 左侧选 **Devices**，等几秒，列表里会出现平板和 `SushiVIP` 的 WebView
4. 点它下面的 **inspect**，弹出一个开发者工具窗口
5. 切到 **Console** 标签，输入下面这行，回车：

```js
SushiVIP.diagnose()
```

> ⚠️ 只有 **debug 包**能 inspect。正式 release 包连不上开发者工具 ——
> 联调阶段请用 debug 包。

### 期望看到什么

会打印一张表格：

| 字段 | 期望值 | 不符时是什么问题 |
|---|---|---|
| 运行在容器内 | `true` | `false` = UA 被改写了，桥接认不出容器 |
| 容器版本 | `1.0.0` | — |
| **安全上下文(HTTPS)** | `true` | `false` = 页面还在 http 上 |
| **AppBridge 可用** | `true` | `false` = 当前域名不在 APK 白名单里 |
| 相机 API 可用 | `true` | 本系统用不到，`false` 也不影响 |
| crypto.subtle 可用 | `true` | 本系统用不到 |
| **设备ID** | `{id: "…", source: "native"}` | ⚠️ 见下 |
| 视口 | 平板实际分辨率 | 数值明显偏小 = viewport meta 有问题 |
| UA | 结尾有 `SushiVIP/1.0.0` | 用它区分 debug / release 包 |

### 🔴 `设备ID.source` 是重点

- **`"native"`** → 正常，取到了平板的 ANDROID_ID
- **`"browser"`** → **不正常**，说明桥接没生效，退回了本地随机串
  （值形如 `PAD-A3K9X`）。这种 ID 清一次应用数据就变，不能作为设备身份。

`source` 是 `browser` 时按顺序查：

1. `AppBridge 可用` 是不是 `false`？→ 域名不在白名单
2. `运行在容器内` 是不是 `false`？→ UA 被中间层改写
3. 两个都 `true` 却仍是 `browser` → Console 里会有一条
   `[pad] 原生设备 ID 获取失败` 的警告，把它发给开发

### ⚠️ debug 包和 release 包的设备 ID 不一样

`ANDROID_ID` 按**应用签名**派生。用 debug 包建的设备档案，
换成正式包后**会全部对不上号**。

**正式建档一定要用 release 包采集。** 联调阶段的数据当测试数据处理。

## 附：给容器（APK）工程师的加固清单

> 背景：现场反馈「平板熄屏一会儿再打开就要求重新登录」。
> 根因是 **Android WebView 的 Cookie 默认只在内存里，要 `flush()` 才落盘**；
> 熄屏后系统回收 WebView 进程，没落盘的 Cookie 就丢了。
>
> **Web 侧已经自己兜底**（令牌同时存 localStorage + 请求头），
> 所以下面这些**不是上线阻塞项**。做了之后两条路都通，更稳。

### A. 建议做：`onPause` / `onStop` 里 flush Cookie

```kotlin
// MainActivity.kt
override fun onPause() {
    super.onPause()
    // WebView 的 Cookie 默认只在内存里。熄屏/切后台后进程随时可能被回收，
    // 不 flush 的话这次会话的 Cookie 就没了 —— 表现为「再打开要重新登录」。
    // flush() 是同步的，API 21+ 起替代了已废弃的 CookieSyncManager。
    android.webkit.CookieManager.getInstance().flush()
}

override fun onStop() {
    super.onStop()
    android.webkit.CookieManager.getInstance().flush()
}
```

### B. 必须确认：DOM Storage 是开的

Web 侧的兜底**依赖 `localStorage`**。

```kotlin
webView.settings.domStorageEnabled = true      // 必须
android.webkit.CookieManager.getInstance().setAcceptCookie(true)   // 默认就是 true，确认一下
```

> 现状判断：Pad 的**设备号**（`vip_device`）和**界面语言**本来就存在 localStorage 里，
> 而这两样在现场是正常的 —— 说明这一项**已经是开的**。
> 只要设备号在同一台平板上保持不变，就是证据。

### C. 🔴 不要做的三件事

| 不要 | 为什么 |
|---|---|
| **不要阻止息屏**（`FLAG_KEEP_SCREEN_ON` / `android:keepScreenOn`） | 门店明确要求息屏省电。会话要能扛住息屏，而不是靠不息屏回避问题 |
| **不要在退出/onDestroy 里清 Cookie 或 WebStorage** | `CookieManager.removeAllCookies()`、`WebStorage.deleteAllData()` 会把会话和设备号一起清掉，症状和这次一模一样 |
| **不要开无痕 / 每次启动清缓存** | 同上。缓存可以清，**Cookie 与 DOM Storage 不能清** |

### D. 怎么验证修好了

1. 平板上登录 Pad
2. 熄屏，**等 3–5 分钟**（要让系统真的回收进程，锁屏几秒不够）
3. 亮屏、打开应用

**期望：直接进主界面，不出现登录页。**

> 更狠的验法：开发者选项 →「不保留活动」打开，或
> `adb shell am kill net.sushisom.sushivip`，再打开应用。
> 这是直接杀进程，比自然回收更严格。

### E. 关于设备号

`vip_device` 存在 localStorage 里，形如 `PAD-A3F9K`。它进审计日志，
用来回答「这笔是哪台平板记的」。

**清了 localStorage 就等于换了一台新平板**（会重新生成一个号），
历史审计对不上人。这也是 C 表里第二、三条的另一个理由。

## 附：常见现象速查

| 现象 | 最可能的原因 |
|---|---|
| 白屏 | 证书不受信任（APK 内置 CA 与服务器证书对不上） |
| 「无法连接服务」 | 真的连不上；服务没起或网络不通 |
| 「服务器返回的不是 JSON」 | 服务端 fatal 或 API 路径不对，提示里带 HTTP 状态码和报文开头 |
| 「服务未正确部署…B001」 | `open_basedir` 把程序目录挡在外面 |
| 按返回直接问退出 | `ui.js` 没加载 |
| 点确认按钮没反应 | `ui.js` 没加载（`UI` 未定义） |
| 设备 ID 是 `PAD-xxxxx` | 桥接没生效，见阶段二 |
| 套餐数量显示 0 | 业务问题，用 `why.php --invoice` 查 |
