## 一、服务端调整

### 1.1 上 HTTPS（P0，阻塞项）

见 [`执行说明.md` 阶段一](执行说明.md)。这是整个项目的前置条件。

**根本原因**：Chromium 只在**安全上下文**（`https://` 或 localhost）下提供
`navigator.mediaDevices`。在 `http://` 页面里它是 `undefined` —— 不是权限被拒，
是 API 根本不存在。App 端已经做了全部能做的配置，但没有任何客户端手段能绕过这条内核规则。

顺带一并解锁（这些在 `http://` 下**同样全部不可用**）：

| API | 用途 | http:// | https:// |
|---|---|---|---|
| `navigator.mediaDevices` | 扫码取流 | ❌ undefined | ✅ |
| `crypto.subtle` | 前端加解密/签名 | ❌ undefined | ✅ |
| Service Worker | 离线缓存 | ❌ | ✅ |
| `navigator.clipboard` | 复制到剪贴板 | ❌ | ✅ |
| Geolocation | 定位 | ❌ | ✅ |

> 如果现有前端代码里有 `if (crypto.subtle)` 之类的兼容分支，上了 HTTPS 之后
> 会走进以前从没走过的路径，需要回归测试。

### 1.2 CORS（P0，若存在跨域）

**必须由服务端解决。原生 WebView 没有任何开关能关闭 CORS。**

需求文档里写的「放开跨域限制」是个常见误解 —— `setAllowUniversalAccessFromFileURLs`
之类只对 `file://` 页面有效，页面走 http(s) 加载时跨域策略完全由内核和服务端
`Access-Control-Allow-Origin` 响应头决定。

**请先确认：LMS 的接口和页面是不是同域？**
- 同域 → 本条跳过
- 不同域 → 服务端加 CORS 响应头（推荐），或告诉我需要代理的域名/路径，
  我在原生层用 `shouldInterceptRequest` 转发（**注意该 API 拿不到 POST 请求体，
  只能代理 GET**，所以这条路走不远）

容器已处理的是相邻但不同的两件事：混合内容放行（HTTPS 页面可加载 HTTP 子资源）、
明文流量放行（过渡期用）。这两项跟 CORS 无关。

### 1.3 Cookie 属性（P1）

容器已开启 Cookie 持久化和三方 Cookie，正常情况下登录态会保持。但请检查服务端下发的 Cookie：

| 属性 | 建议 | 说明 |
|---|---|---|
| `Secure` | 上 HTTPS 后可以加 | 加了之后 http 回退访问会丢登录态，与 6.4 步关闭明文回退配套 |
| `SameSite` | `Lax` 或 `None; Secure` | 设成 `Strict` 在部分跳转场景会丢 |
| `Domain` | 与 `lms.sushisom.net` 一致 | 如果将来改用 IP 直连兜底（`https://192.168.2.32`），带 `Domain` 的 Cookie 会失效 |

### 1.4 不要用 UA 黑名单拦截 WebView（P1）

容器的 User-Agent 在标准 Android WebView UA 后追加了 ` SushiVIP/1.0.0`。
如果 LMS 有「请使用 Chrome 浏览器访问」之类的 UA 检测，**要把这个标识加进白名单**，
否则用户一进 App 就被拦在提示页。

## 二、前端：容器能力对接

### 2.1 引入桥接封装（P0）

把 [`sushivip-bridge.js`](sushivip-bridge.js) 放进静态资源目录并引入：

```html
<script src="/static/sushivip-bridge.js"></script>
```

它解决三件事：同一份代码能同时跑在容器内和 PC 浏览器（方便开发）、
原生调用失败有降级不炸页面、提供 `SushiVIP.diagnose()` 联调命令。

### 2.2 设备唯一标识（P0）

```js
const { id, source } = SushiVIP.getDeviceId();
// source === 'native'  -> 来自 ANDROID_ID，可作为设备身份依据
// source === 'browser' -> 浏览器兜底，仅供开发调试
```

**不要直接调 `window.AppBridge.getDeviceId()`**，在 PC 浏览器里会抛
`TypeError: Cannot read property 'getDeviceId' of undefined`。

⚠️ **两条必须传达给后端的约束：**

1. `ANDROID_ID` 按「应用签名 + 用户 + 设备」派生，**debug 包和 release 包
   在同一台平板上取到的值不同**。联调阶段用 debug 包建的设备档案，
   换成正式包后会全部对不上号 —— **正式建档必须用 release 包采集**。
2. 恢复出厂设置、多用户切换、应用分身都会改变这个值。如果业务上要求
   「一台设备终身唯一」，需要在后端配合人工换绑流程，纯靠客户端做不到。

### 2.3 扫码（P0）

站点上 HTTPS 后直接用标准 Web API，容器侧已配好全部支撑：

```js
// 先做能力检测，给出可读的错误提示
if (!SushiVIP.cameraSupported()) {
  alert('相机不可用，请联系管理员');
  return;
}

const stream = await SushiVIP.openCamera();   // 默认后置摄像头
videoEl.srcObject = stream;
await videoEl.play();
```

**`<video>` 元素必须带这三个属性**，缺任意一个在部分场景下不起播：

```html
<video autoplay playsinline muted></video>
```

容器侧已处理：Manifest 权限声明、运行时权限动态申请、`onPermissionRequest` 放行、
`mediaPlaybackRequiresUserGesture = false`（**少这一项取景框全黑且无任何报错**）。

**用完记得关流**，否则相机指示灯常亮、后续页面再取流会失败：

```js
stream.getTracks().forEach(t => t.stop());
```

> 扫码识别用哪个库由前端自选（jsQR / zxing-js / BarcodeDetector）。
> 如果实测在平板上识别慢或暗光扫不出来，告诉我，我可以在容器侧加一个
> 原生扫码接口（CameraX + ZXing），性能会好一个量级。

### 2.4 拍照上传（P0）

```html
<input type="file" accept="image/*" capture="environment">
```

容器已完整实现文件选择链路：

| 写法 | 容器行为 |
|---|---|
| 带 `capture` | 直接拉起系统相机 |
| 不带 `capture` | 弹出「相机 / 相册·文件」二选一 |
| 带 `multiple` | 支持多选 |

**这条走的是与扫码完全不同的技术链路**（`onShowFileChooser` → 系统相机），
不依赖安全上下文，即使在 http 下也能用。

### 2.5 容器检测（P2）

```js
const { inContainer, version } = SushiVIP.container();
```

用于差异化处理，例如：容器内隐藏「下载 App」引导、隐藏浏览器才有的操作提示、
容器内启用扫码入口而浏览器里隐藏。

## 三、前端：UI / 交互适配

### 3.1 固定横屏（P1）

平板锁定横屏（充电口朝右），**页面永远不会收到竖屏尺寸**。

- 如果 LMS 有针对竖屏的移动端布局，那套分支在容器里永远走不到
- 请按平板实际分辨率验证布局，不要只在 PC 浏览器缩放窗口测

### 3.2 没有浏览器 UI（P1）

容器是沉浸式全屏：**没有地址栏、没有刷新按钮、没有前进后退按钮**。

| 需要提供 | 说明 |
|---|---|
| 页内刷新入口 | 页面卡住时用户没有别的办法，只能杀进程重启 |
| 页内返回/关闭按钮 | 物理返回键虽然可用，但不直观；深层页面建议有面包屑或返回 |
| 明确的错误提示 | 接口失败时不要静默，用户看不到浏览器的任何错误提示 |

**返回键行为**（容器已实现）：
- WebView 有历史可后退 → 执行网页后退
- 已在首页再按 → 弹「确认退出」对话框

> 如果 LMS 是 SPA 且用 `history.pushState` 做路由，路由变化会计入 WebView 历史，
> 返回键会按预期逐级后退。若用 `history.replaceState` 或纯前端状态机（不写历史），
> 返回键会**直接跳过中间步骤退回上一页**，多步表单场景需要注意。

### 3.3 缩放已禁用（P1）

容器关闭了双指缩放（`setSupportZoom(false)`）。页面必须在平板原生分辨率下直接可读，
不能指望用户放大。请确认最小字号、表格、密集表单在实机上的可读性。

### 3.4 viewport meta（P1）

容器开了 `useWideViewPort` + `loadWithOverviewMode`。**页面必须有标准 viewport meta**：

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
```

- **缺这个 meta**：WebView 会按 980px 虚拟宽度渲染再缩放适配，
  在平板上表现为整体被缩小、字变小
- **`viewport-fit=cover`**：容器是全面屏沉浸模式，内容会延伸到屏幕物理边缘。
  如果平板有挖孔/圆角，需要配合安全区避让：

```css
.app-header { padding-left: env(safe-area-inset-left); }
.app-footer { padding-right: env(safe-area-inset-right); }
```

（横屏下要关注的是 `left`/`right`，不是 `top`/`bottom`）

### 3.5 软键盘遮挡（P1，横屏尤其严重）

横屏下软键盘会占据接近一半屏幕高度。请确认：

- 登录框、搜索框、表单输入项在弹出键盘后**仍然可见**
- 输入框获得焦点时主动滚动到可视区：

```js
input.addEventListener('focus', () => {
  setTimeout(() => input.scrollIntoView({ block: 'center', behavior: 'smooth' }), 300);
});
```

> 这一项容器侧也需要配合调整，见第五节。

## 四、前端：需要避开的写法

这一节最重要。以下写法在容器里的表现是**静默失败** —— 没有报错、没有提示、
点了完全没反应，排查起来极其耗时。

### 4.1 ❌ `window.open()`（P0）

容器未开启多窗口支持，`window.open()` 会**返回 null 且什么都不发生**。

```js
// ❌ 静默失败
window.open('/course/123');

// ✅ 改为同页跳转
location.href = '/course/123';
```

**请全局搜索 `window.open`**，逐个替换。

### 4.2 ❌ 下载链接（P0）

容器未实现 `setDownloadListener`，以下写法点击后**没有任何反应**：

```html
<!-- ❌ 直接指向文件的链接 -->
<a href="/export/report.xlsx">导出报表</a>
<a href="/files/课件.pdf" download>下载课件</a>
```

```js
// ❌ Blob 下载
const url = URL.createObjectURL(blob);
a.href = url; a.download = 'x.xlsx'; a.click();
```

**LMS 大概率有导出报表、下载课件、下载证书这类功能，请务必排查。**
两条解决路径见第五节 —— 大多数情况我建议由容器侧实现下载支持，前端不用改。

### 4.3 ❌ PDF 直链预览（P2）

**Android WebView 不能渲染 PDF。** 指向 `.pdf` 的链接在容器里会变成一次下载
（而下载又没实现），结果就是白屏或无反应。

| 方案 | 说明 |
|---|---|
| **前端集成 pdf.js**（推荐） | 在页面内渲染，体验统一，容器无需改动 |
| 服务端转图片 | 简单可靠，但失去文字选择/搜索 |
| 容器侧交给系统 PDF 阅读器 | 会跳出 App，体验割裂，且平板需预装阅读器 |

### 4.4 ⚠️ `target="_blank"`

容器未开启多窗口，`target="_blank"` 的链接会在**当前 WebView 内**打开
（不是新窗口）。功能上可用，但用户会失去「关掉新标签页回到原页」的心智模型，
建议改成同页跳转并提供明确的返回入口。

### 4.5 ⚠️ `alert` / `confirm` / `prompt`

可用，弹的是系统默认样式对话框，标题会显示页面来源地址，不太美观。
重要交互建议改用页内弹层组件。

### 4.6 ⚠️ Service Worker 缓存

上 HTTPS 后 SW 可用了。但要注意：**SW 缓存的资源会跨 App 升级持续存在**，
发版后用户可能仍在跑旧版前端。如果启用 SW，务必设计好版本更新与缓存失效策略。

### 4.7 ⚠️ 站外链接会跳出 App

容器只允许在白名单域名（`lms.sushisom.net`、`192.168.2.32`）内导航，
其他 http(s) 链接、以及 `tel:` `mailto:` `weixin://` `alipays://` 等
**都会转交给系统处理，用户会离开 App**。

如果有第三方域名的资源需要留在 App 里打开，把域名告诉我加进
`HOST_WHITELIST`（在 `app/build.gradle.kts`）。

## 五、需要容器侧配合的三项（请前端确认后反馈）

这三项是容器当前的能力缺口。每项都有「前端规避」和「容器实现」两条路，
**需要你们确认哪种更合适**。

Web 侧已完成排查，结论如下：

| # | 缺口 | Web 侧排查结果 | 处理 |
|---|---|---|---|
| 1 | 文件下载无反应 | 下载入口 **0 处** | 暂不实现。若将来新增下载功能，**必须同步通知容器侧**——否则表现是点击毫无反应，无任何报错 |
| 2 | `window.open()` 静默失败 | `window.open` **0 处** | 暂不实现，同上 |
| 3 | 软键盘遮挡输入框 | — | 仍建议前端在输入框 focus 时 `scrollIntoView` 兜底 |

> 第 1、2 项的共同风险是**失败方式不可见**。它们各自只需约 5 行容器代码，
> 需要的话说一声，我随时加上，成本远低于将来排查一个「点了没反应」。

## 六、联调检查清单

平板 USB 连电脑，Chrome 打开 `chrome://inspect` → 找到 SushiVIP 的 WebView → **inspect**
（仅 debug 包可调试）。

在 Console 里执行：

```js
SushiVIP.diagnose()
```

**期望输出**：

| 字段 | 期望值 | 不符时 |
|---|---|---|
| 运行在容器内 | `true` | UA 被中间层改写了 |
| 安全上下文(HTTPS) | `true` | **站点还在 HTTP，回服务端阶段一** |
| AppBridge 可用 | `true` | 当前页面不在域名白名单内 |
| 相机 API 可用 | `true` | 同「安全上下文」 |
| crypto.subtle 可用 | `true` | 同上 |
| 设备ID.source | `'native'` | 桥接未生效 |
| 视口 | 平板实际分辨率 | 检查 viewport meta |

**逐项功能验证**：

- [ ] 设备 ID 返回 `source: 'native'` 且值非空
- [ ] 扫码：取景框有画面（不是黑屏），能识别二维码，关闭后指示灯熄灭
- [ ] 拍照上传：能拉起相机、能选相册、图片成功上传
- [ ] 登录后杀进程重开，**登录态仍在**
- [ ] 全局搜索确认 `window.open` 已清零
- [ ] 所有下载/导出入口已列出清单并反馈
- [ ] 横屏布局在平板实机分辨率下无错位
- [ ] 弹出软键盘后，输入框仍可见
- [ ] 返回键逐级后退符合预期，首页按返回弹确认框
